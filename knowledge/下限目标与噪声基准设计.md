## 0. 先把"对照"这个词拆成两件事（当前它们是同名的）

现状：`clean_subject`（夹具名 CLEAN）同时被当作**两件事**，这是混淆的根源：

| 真实概念 | 现在叫什么 | 谁需要它 | 用途 |
|---|---|---|---|
| **改前基线**（改前存盘运行状态，对比改后） | baseline bundle | **Verify**（判"有没有优化"） | 同协议重采、`k·σ`、守护全量对比 |
| **噪声基准**（一台机器不干活时抖多少） | 也叫 CLEAN | **Detect**（判"算不算异常"） | 标定噪声带、偏离倍数 |

**你的优化判据用的是第一行**（改前/改后），它一直成立、不需要无缺陷场景。
那条"禁止判定（§8.1）"硬闸拦的是第二行：没有第二行，就不知道噪声带该画在哪。
所以"没有无缺陷场景"推翻的是**必须有第二个场景**，不是推翻"必须有参照物"。

命名建议（代码/文档/报错三处同步，否则下一个人还会踩）：
- `clean_subject` → 语义保留，但文档/文案统一叫**噪声基准（noise_baseline）**；
- Verify 的 before/after 明确叫**改前基线 / 改后基线**。

## 1. 去掉硬拒：噪声基准缺失 ⇒ 口径降级，不是整轮拒判

`patrol_waterline` 现在（patrol.py:196-200、:355-356）在"本轮没采到噪声基准"时
**整轮返回盲区、不出任何结论**。真实工程没有无缺陷场景 ⇒ 这条会把自动巡检
自我否决。改成**噪声带来源分级**，每级都能出结论，但声明弱在哪：

```
来源等级（弱→强）：
  L0  无噪声基准        → 只走绝对门槛（见 §2），出 finding 标 noise_basis="none"
  L1  跨轮次历史波动     → 同场景多次采样的 σ 当噪声带，noise_basis="historical"
  L2  同期噪声基准在场    → 现状（最强），noise_basis="concurrent"
```

**硬门禁不变**（防止"降级"变成"放松到什么都算检出"）：
- L0/L1 下**不允许输出"误报率"**——FP 率只有 L2 可测（对照自比自才有意义），
  按 G15"成对展示"与 G20"盲区声明"，报告里 FP 率标 `not_measurable`，
  不许留空冒充 0。
- L0 下只能报"**越绝对线**"，不能报"相对抖动显著"——即 `k·σ` 那条分支禁用，
  与现有 `degenerate_distribution` 走 `min_magnitude` 绝对门限是同一写法，
  可复用，不新判据。
- 等级写进 `TraceSpan`/detection 结果，跨 run 比较时并入 G7（L2 与 L0 的数据
  **不可混比**：一个是相对显著、一个是绝对越线，语义不同）。

**为什么方向是放松不是收紧**：L0 出的是"越线事实"，比 L2 的"相对显著"门槛更
**高**（绝对线通常远大于噪声带），所以降级只会少报、不会虚报，符合"宁缺毋假"。

## 2. 绝对下限目标表（"提下限"的操作入口）—— 必须带出处才合法

`detector.py:25-41` 有一条既有硬规则：**阈值只能来自①噪声标定，或②带
`budget_ref` 出处的帧预算锚点；无出处的绝对线 = 手调，构造期直接拒收**。
这条恰好和你的诉求对上——你要的"下限"不是检测器的抖动阈，而是**工程目标线**
（帧预算、draw call 上限）。二者本就应分开建模，下限表就是预算线那一类的泛化。

### 与既有 `frame_budget` 通路的关系（先读实况再写的这节）

模式不是新发明的：**仓库里已有带出处的绝对线**。`knowledge/frame_budget.json`
（16.7/33.3ms 两条预算 + 引用来源）被注册表第 5 条检测器
`DET-LOAD-FRAMESPIKE` 以 `threshold_source="frame_budget"` + `budget_ref` 引用，
构造期校验"无出处=手调拒收"就是为它建的。所以 §2 是**这条既有腿的推广**，
不是新阈值体系：

| | 现有 frame_budget |  proposed 下限表 |
|---|---|---|
| 指标 | 仅 frame_time_ms | 任意已注册指标（drawCalls 等） |
| 输入形态 | BreachSample（逐帧发作） | 窗口统计（水位）+ 分位（p95/p99） |
| 消费链 | m2a_detect_breach（episode 通路） | 水位通路第二条腿 |

⚠️ 关键区分（不能并成一张表的原因）：**预算线是外生约束（目标帧率的算术导出），
目标线是提标手段（人为逐步收紧）**。前者改了要重跑标定链，后者改了只进
protocol 指纹重评检出范围。硬把它们塞进一个文件，就会重演
"窗口标定覆盖帧预算线（两套阈值体系互相污染）"——m1_detect.py:295-299
注释里记录过这个实测教训，两条腿必须物理分开。

### 表长这样（每工程一份，随 ProjectProfile）
```jsonc
// <profile>/floor_targets.json —— 目标线来自产品/性能预算，不是调参
{
  "source": "性能预算 v3 · 主机平台 60fps",   // 出处（对应 budget_ref 的强制要求）
  "targets": [
    { "metric": "frame_time_ms",       "op": "p95<=", "value": 16.7, "unit": "ms" },
    { "metric": "drawCalls",           "op": "<=",    "value": 1500,   "unit": "calls" },
    { "metric": "cpuFrameTimeMs",      "op": "p99<=", "value": 25.0,   "unit": "ms" }
  ]
}
```

- `op` 支持 `<=`（均值/水位）与 `p95<=`/`p99<=`（最差分位）。**下限应盯 p95/p99**
  （体感卡顿来自最差帧，不是均值）——这条来自上轮讨论，均值会骗人。
- 表缺失 ⇒ 该工程**不启用绝对线**（不猜默认阈值，遵守"配置缺段=不启用"）。
- 出处字段**必填**：否则等于 §8.1 明令禁止的手调。UI 里这栏不给留空。

### 与噪声标定的关系：并行，不互相覆盖
- 现有水位判据（`compare()`）继续用噪声标定测"相对异常"。
- 下限表是**第二条腿**：指标越绝对线 ⇒ 独立产出一条 `ptype=waterline`
  但 `basis="floor_target"` 的 finding，与相对检出互证或各自单列。
- 提标操作 = **只改这张表的 value**，不碰 `thresholds_*.json`（那是标定产物，
  属 §3 维度一 blocked，不该手改）。这就把"提高下限压力"变成一个可编辑、
  可审计、有出处的动作，而不是去调检测器阈。

### G14/G7 配套（避免提标污染历史）
- 表内容摘要（哈希）进 `protocol_fingerprint`：改了目标线 ⇒ 指纹变 ⇒ 与旧轮次
  不可混比（提标本就该重评，这正是你要的"瓶颈重新暴露"的干净边界）。
- 一次提标的"大面积检出"不当作回归：见 §3。

## 3. 提标后的分流：瓶颈"尚未解决" vs "手段用尽"（#24 的核心，提前对齐）

你提的机制（提标→瓶颈暴露→继续修→修不成出报告）里有个必须防的失效：
阈值是**检测器不是修复器**。把线提到当前物理水平之上，结果必然是大面积检出，
若照旧烧 `max_attempts_per_issue` 去修一个"手段还没到位"的目标，产出的是
配额空烧 + 满屏 failed。所以在唤起修复前先分流：

```
越绝对线的指标 finding 进修复循环前，先看：
  有对应 playbook 模板 / 有未试过的 Hypothesis  ⇒ 正常进 fix（"尚未尝试"）
  同 Issue 签名已试过且失败 N 次、无新假设来源  ⇒ needs_human + 出总结报告
```

- 失败阈值 N 走配置（复用 `budget.max_attempts_per_issue`，已 UI 可编辑）。
- 报告内容（现有字段基本够，缺的是聚合产物层）：
  `下限画像`（本轮各指标 vs 目标线）＋ `试过的方向`（Hypothesis[] + EditPlan diff）
  ＋ `为什么没成`（Verdict：not_significant / regressed / perception_failed）
  ＋ `下一步候选`（potential 里 slope_source 指向该指标、尚未 promoted 的条目）。
- 这条不是新架构：Issue 记 `failed` 时保留全证据链已是 §1.6/§1.7 既有规则，
  #24 只是把它攒成人读报告。

## 4. "检测端一个常驻探针即可？" —— 调研结论 + 卡点（子代理联网核实）

你列的下限指标里，**平均/峰值帧耗时、GC、Animator** 可由一个常驻注入探针全包
（逐帧 CPU/GPU 时间一条流，水位与发作是同一份数据的两种聚合）。合并收益真实：
现在 A/A2/A4 三档 = 三条采集路径，同一指标可能两源、G7 要防跨源混比；合并后
"发作"与"水位"同源、开销标定只管一件事。

**但 draw call 这一项卡住**（实测 + 官方 Issue 双向印证）：
- 我们实测：注入回调读渲染 counter=0、离线 `.data`=−1 哨兵，只有 GUI 外部轮询拿得到。
- 官方已知缺陷 **UUM-127894**：设了 `targetFrameRate` 后 `ProfilerCategory.Render`
  全为 0；6.0/6.1/6.3/6.4 已修，**6.2 Won't Fix**；绕法=
  `ProfilerRecorderOptions.StartImmediately` 或强开 `ProfilerDriver.enabled`。
  我们的 Editor 是 **6000.6.7**，落在"已修"区间——**值得先按版本号重测绕法**，
  这是唯一"零新组件"的单源路径。
- 另有 UUM-131281（6000.4/6000.5 URP Play 渲染整列 0），6000.5.0a7+ 修，6.0 系未复现。

**结论**：能不能单探针，取决于 `ProfilerRecorder(Render)` 在 6000.6.7 的 Play 里
能否拿到每帧 draw call——**目前没有实测证据，不能当已知**。排序：
1. 先做**一次性 eval 实验**：Play 里用 `StartImmediately` 起 recorder 落盘读 Render
   计数 → 成了就规划"探针单源 + 双跑等价性迁移"，不成就明确保留"探针+轮询"两源，
   并把结论写进 G16 别再挂着。（需 Editor 实跑，我可以发起，但要你同意开 Editor。）
2. 兜底：CLI 有 `diagnostics profiler_record`（录 .data）+ 第三方解析器
   `unity3p-jp/ProfilerReader`（但仅到 2022.3、且在 Editor 内跑，适配存疑）。
3. `batchmode` 出真数、SRP 回调取数、FrameCapture：**均未找到支持证据**，不建议投入。

**迁移风险**（无论走哪条）：单源后探针一旦失真/被卸载，全链路同时失明；现在三源
分离反而一条坏了另两条能出结论。所以**不直接切，先双跑等价性验证**——旧轮询与
新探针并行采一段，同指标差异落在噪声带内才下线旧路，否则是拿一个未验证的信任
替换一个已知偏差的信任。
