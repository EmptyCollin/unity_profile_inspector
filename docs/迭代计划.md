# UPI 迭代计划（v2：两形态 + 探针优先 + UI 唯一通道）

> 状态：**执行中**。最后更新：2026-11-12（I7 方向修正；I7b 优先）。
> 本文是后续开发的单一路线图；与旧 DESIGN/AGENTS 冲突时，以本文 + 对应 ADR 为准。
> ADR：`docs/adr/0001`~`0005`。

## 0. 目标形态

一个本地常驻的 Unity 性能 Agent：

> **一个探针、两种形态（常驻 / 回归）、一套事件-聚类-指纹-修复核心；所有人类操作只通过本地 Web 控制台完成，CLI 只保留启动、诊断和应急。**

### 两种形态

| 维度 | 常驻形态（日常开发） | 回归形态（批量回归） |
|---|---|---|
| 数据源 | 常驻探针 + 1Hz 哨兵/抽检 | 确定性 replay + 测试目标 |
| 问题定义 | 预算线 / 相对基线 / 抽检异常 | replay 指令 + 测试目标 |
| 复现 | 不要求 3 次基线 | 3 次（或 N 次）基线 + 聚类 + 复现率 |
| 修复 | best-effort，编译/冒烟/可回滚 | 修 + 同 replay 重跑 + 重新聚类 |
| 结论 | `unverified`，不进成功率分母 | `verified`，进成功率 |
| 节奏 | 常驻 / 实时 | 批量 / 夜间 / CI / 里程碑 |

**硬规则**：常驻不得记 `resolved/verified`；回归的 `verified` 必须来自“同 replay、同 cluster 消失、无新 cluster、守护不劣化”。

## 1. 五条架构定调

1. **单探针**：合并两个注入件，一个回调、一个心跳、一条事件流；用户三态开关（关/稳态/全程）。1Hz 轮询只做哨兵。
2. **事件两类**：`breach`（确定越界，进修复循环）、`sample`（不确定抽检，只产候选）。
3. **cluster 是单位**：一个 replay/巡检里多个相同/不同问题先聚类再分类；修复和验证都以 cluster 为单位。
4. **批量工单、串行落地**：工单可列多个候选，按置信度排序；一次只落一个 patch，每步 snapshot → 编译/冒烟 → 观测 → keep/rollback → 下一个。
5. **UI 唯一通道**：本地 Web 控制台；文件只作审计载体；CLI 只启动/诊断/应急。

## 2. 数据与验证等级

```text
ProbeEvent(kind=breach|sample, frame, metric, value, series/ring, a4, protocol_fp)
IssueCluster(cluster_id, metrics, rel_range, shape, occurrences, reproduction_rate)
Fingerprint(features, pattern_id, root_cause, playbook_id, confidence, stats)
BatchTicket(id, mode, items[], status)
PatchAttempt(ticket_id, patch, snapshot, safety, observation, decision)
Verdict(mode, verification=unverified|observed|verified|failed, target, guards, new_clusters)
```

统计必须分账：`mode ∈ resident|regression`、`verification_status ∈ unverified|observed|verified`。

### 3.1 I7 方向修正（权威）

- **产品目标**：不是“修好人为植入缺陷”，而是“找到相对可达参考值得做、做得到、
  可验证的优化机会”。`Issue`（越界/回归）与 `Opportunity`（无越界但有差距）分账。
- **CLEAN 退出产品**：不再当目标/负对照；噪声来自同场景重复运行，合格线来自
  floor/budget，机会参考来自 peer/history/static/algorithmic；`zero-to-zero=unassessed`。
- **去夹具化**：`_refs`/`defect_ref`/`fix_subject`/按行切片只允许测试；
  产品 planner 从当前源码+证据生成 diff，不得按 `profile_id` 分流。
- **工程选择**：修复对象必须在 UI 中选；保留最近/收藏/校验/归档/历史；
  活动工程绑定所有操作，运行中禁止切换。
- **真实开发模拟工程**：`sim/project`（Chroma Rogue，三消+轻肉鸽）统一入口/默认场景
  + 18 常规 + 3 混合 + 3 负对照（共 24）；oracle/replay 由评估者持有，不进工程；
  replay 改为项目指令序列，UPI 工具执行，UPI 内 Agent 隔离；Addressables 24/24 已通，
  全包体 <30MB。当前 24 case 评测通过，I8 起按真实项目边界重构。
- **不保留兼容性**：工具尚无使用者/历史包袱；旧 `projects/*.json`、旧 API/CLI
  可直接替换，不做迁移层/双读/fallback；`ProjectRegistry` 是唯一事实源。
- **视觉/交互重设计**：主界面只保留「开始游戏 / 说明 / 专项测试下拉」；2.5D 色块、
  拖拽交换、消除/掉落动效、倒计时进度条、BONUS 可见化；详见 `docs/视觉设计.md`。
- **验收**：I7b 先做到“无 JSON 手编即可选择并恢复工程”；I7c/I7d 做到
  “无 clean 也能机会发现、未见工程可生成/拒绝”；I7e 不是只测 CPU；
  I7f 才是真实用户工程验收。

## 4. 验收

### 常驻形态
开探针 → 检出 breach/sample → 聚类 → 批量工单 → UI 批准 → 2+ patch 串行 → 一个失败回滚 → 全程 `unverified` 留痕。

### 回归形态
定义 replay + 测试目标 → 3 次基线 → cluster 矩阵 → 稳定 cluster → 修复 → 同 replay 验证 → `verified` 报告；失败可回滚。

### UI
所有人类操作在 UI 完成；不手工编辑 JSON/Markdown；CP936 正常；localhost 安全；关键流程有浏览器冒烟测试。

### 工程
旧测试保持绿；新增事件/聚类/指纹/执行器/UI API 测试；README/使用说明改为 UI 口径；旧 ANSI TUI 删除或标 deprecated。

### 工程选择/管理（I7b）
- 无 JSON 手编：UI 新增/选择/编辑/校验/归档工程；
- 最近工程与上次场景/质量档/模式自动恢复；
- 活动工程绑定所有探针/建单/执行/回归/报告，运行中禁止切换；
- 路径失效 fail-closed，不回退夹具；有历史 run 只允许归档，物理删除二次确认。

### 机会发现（I7c/I7d）
- 无 clean 也能产 `OpportunityFinding`（floor/budget/static/peer/history）；
- 无参考时 `insufficient_evidence`；无机会工程不硬造 plan；
- `Opportunity` 与 `Issue` 分章、分账，不混入 resolved/verified；
- 未见工程可从当前源码生成或明确拒绝，不依赖 `_refs`/profile-id。

### 8.4 LLM 主体后的链路（含容错与反馈）

```text
证据（测量）
→ LLM 诊断（六因子 + 根因候选 + 证据引用）
     ↳ 输出非法/超时/限流 → 重试/降级（见 8.5）→ 仍失败则 needs_human
→ LLM 规划（结构化补丁草案，或 insufficient_evidence）
     ↳ find 不唯一/不命中 → 把“实际源码片段 + 错误”回喂 LLM，最多 2 轮
     ↳ 编译失败 → 把编译器错误回喂 LLM，最多 2 轮
→ 确定性执行：快照 → 精确 apply → 编译 → 可运行冒烟 → 失败回滚
→ 复验：同 replay 前后 observed；满 3 基线才 verified
→ 写入本项目历史（供下次参考，不直接复用）
```

规划输出契约（新）：

```json
{"why": "...", "edits": [{"file": "Assets/...", "find": "...", "replace": "..."}]}
```

执行器只做三件事：精确命中校验、应用、编译；不猜意图、不做模板替换。

### 8.5 容错与反馈（硬要求）

| 失败点 | 处理 |
|---|---|
| 连通性/鉴权/模型不存在 | 熔断：不重试同类请求，标 `llm_unavailable`，转人工；记录原因 |
| 超时/限流/5xx | 按配置退避重试（默认 2 次）；仍失败 → 结构化失败，不阻塞后续候选 |
| 输出非 JSON / 缺字段 | 修复性重试 1 次（附错误）；仍失败 → 该候选作废并留痕，继续下一个 |
| tool call 不被支持/报错 | 降级为纯 JSON 输出；仍不支持 → 标 `tool_unsupported`，不重试 |
| 补丁 find 不命中/命中多次 | 回喂实际源码与错误，最多 2 轮；仍失败 → 记“未能规划”，转人工 |
| 编译失败 | 回喂编译错误，最多 2 轮；仍失败 → 回滚 + `compile_failed_rolled_back` |
| 任一轮次超预算 | 停止该 Issue，保留全部记录，转人工 |
| 进程崩溃/断线 | 每阶段落盘；resume 从最后完成阶段继续，不重复已花调用 |

通用规则：

- 每次 LLM 调用都记 token/耗时/重试/错误类型；
- 单个失败不得让整轮考试卡死或静默；最差结果是 `needs_human` + 原因；
- 重试有上限（默认 2），禁止无限循环；
- 提示词泄漏筛查 fail-closed（命中 test/oracle/case 等词直接拒发）。

## 9. I11：模式感知工作流（共享内核 + 能力表）

> 背景：I10 考试暴露了三个问题（编译失败会中断、证据不足无回路、修复后没有复验）；但考试项目有 replay、常驻项目没有。
> 原则：**共享内核，按 mode 给能力；绝不把考试口径套到常驻。**

### 9.1 两条形态的硬边界

| 维度 | resident | regression / 考试 |
|---|---|---|
| 可复现性 | 不保证 | replay 可复现、可对齐 |
| 证据来源 | live 窗口、源码、调用栈、历史 | 上述 + replay 指定帧/窗口 |
| 验证阶梯 | 编译 → 冒烟 → 观察（unverified） | 编译 → 冒烟 → replay 一次 → 3 基线（verified） |
| Agent loop | 事件触发，最多 1 次补证据/重规划 | 可多次，预算更大 |
| 允许结论 | `unverified` / `observed` | 才允许 `verified` |
| 自动落地 | 默认保守，写操作仍走权限闸 | 考试可由用户授权批单 |

### 9.2 共享内核（两模式复用）

- 快照、精确 apply、编译门禁、回滚、预算、trace；
- `EvidenceRequest` 协议与工具白名单；
- 最终可用性门禁：收尾必须可编译/可启动，否则整卷 0（但过程不停）；
- 单修复点失败 = 该点 0，不拖垮整卷（回滚成功的前提下）。

### 9.3 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| I11a | mode 进 state/工单/verdict；能力表（providers、ladder、budgets、auto_apply） | 两模式工具集不同；resident 拿不到 replay 工具 |
| I11b | 编译失败回路：错误回喂规划 ≤2 轮；仍失败回滚；继续下一个；退出时可用性门禁 | 注入编译错误：有界重试、回滚、工程可编译；单点失败不中断 |
| I11c | `EvidenceRequest` 双向链路：分析请求 → 检查定向补采 → delta；≤2 轮、去重、unavailable 不脑补 | 常驻只能 live 补采；回归可 replay 补采；请求不可满足时转人工 |

### 9.4 常驻模式保护（硬要求）

1. 默认路径不变：发现 → 保守修复 → 观察 → 不行回滚；
2. 只有“证据不足 / 编译失败 / 修复后仍复发”才进 loop，且最多 1 次；
3. 常驻工具表里没有 replay，代码层拒绝；
4. verdict 层强制：resident 不得写 `verified`；
5. 预算独立且更小；超预算转人工；
6. 任何失败必须可回滚；最终工程必须可用。

### 9.5 考试模式规则

- 一道题、多得分点；
- 编译失败：回喂重规划 ≤2 → 回滚 → 继续；最终不可用 = 0；
- 修复后先 replay 一次（目标 cluster 消失、无新 cluster），再决定是否跑 3 基线；
- 单次 replay 只作覆盖/回归门禁，不作统计结论；
- 用户授权代理批单；评分看 Agent 的判断与方案。

### 9.6 风险

- 常驻 loop 增加时延/成本 → 触发式 + 小预算；
- replay 单次仍可能偶然通过 → 不升 verified，3 基线后才升；
- 能力表配置漂移 → 单点定义，测试钉住；
- 编译回路与权限闸冲突 → 回喂规划不绕过审批，写入仍要批。

## 10. I12（修订版）：数据链接真 + 采集扩充

> 修订原因：上一版把“动作对齐/负对照”当成方法，违背“所有输入都是带病样本、检测不能预设动作”的前提。
> 本版原则：
> 1. **输入永远是带病样本**；真值只来自注入标签或专家确认，不需要健康对照；
> 2. **检测单元是数据异常，不是 action**；replay 只是负载，不向检测器暴露命令类型；
> 3. 不再要求“干净工程 FP=0”；precision 在标签不完整时标 `unmeasured`；
> 4. 常驻保守、回归可复现，两者共享内核、按 mode 给能力。

### 10.1 目标

| 目标 | 说明 |
|---|---|
| 数据链不再断 | 历史接项目库、证据回路接线、每次尝试都记账、停止原因可解释 |
| 采集覆盖全生命周期 | 常开轻量层 + 环缓冲 + 越界升级 + 通用钩子，不依赖已知动作 |
| 检测可盲测 | 不给 action 语义也能发现异常；给标签才算 recall |
| 评测不循环论证 | 标签召回 + 证据审计 + extra/false 分离；无健康对照要求 |

### 10.2 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **I12a 数据链修复** | ① 历史读写统一到 `runs/projects/<id>/knowledge`；② 考试/回归节点传 `mode` + `evidence_collector`；③ 每次尝试一条 RepairRecord；④ 停止原因落 findings | 连跑两场能读历史；证据请求真的执行；两次尝试 repairs=2；stop_reason 可查 |
| **I12b 采集扩充（盲采）** | 运行时 L0 每帧标量 + L1 环缓冲 + L2 越界升级 + L3 通用钩子；静态 S0 快照 + S1 代码索引 + S2 资产索引 + S3 配置索引 | 未知时刻注入越界，能拿到事前 ring 与事后调用栈；静态证据可按请求补采且标清边界；检测器不读 action 类型 |
| **I12c 异常驱动定位** | 越界判定（绝对门限/滚动基线/变化率/变点）；触发后冻结事前、升级事后；候选按“异常窗口 vs 正常窗口”统计对比排序 | 不依赖 action 也能产出候选；盲区清单显式 |
| **I12d 重试闭环** | `max_steps` 取能力表；`needs_recheck` 继续到 clean/budget/stagnant；失败换下一个 hypothesis；同目标+同 diff 连续两次停 | 假驱动：多轮都 recheck、换假设、停滞即停、原因可查 |
| **I12e 标签入库 + 评测契约** | 标签来自注入清单/专家；输出分 TP / extra / unsupported / FN；precision 无完整标签时 `unmeasured`；action 标签消融 | 隐藏 action 类型后 recall 不明显下降；extra 不记 FP |
| **I12f 报告与图表** | attempts、每轮 ladder、stop_reason、extra、盲区、开销 | 报告能答“为什么停、哪轮失败、漏在哪” |
| **I12g 白纸真考** | 清库 → 重出卷 → live 全链路 → 图表 | 能看到多轮 attempts、盲采证据、extra 分类；无虚报 verified |

顺序：I12a → I12b → I12c → I12d → I12e → I12f → I12g。
I12a 先修账；I12b/c 是检测能力主体；I12d 只修重试语义。

### 10.3 采集分层（I12b 细节）

```text
L0 常开：frame time / GC / drawCalls / batches / memory / loading / marker
L1 环缓冲：最近 N 帧标量 + 最近 marker，越界时冻结
L2 升级：触发后开深档 + 分配调用栈，采 M 帧后关
L3 钩子：Resources.Load / Instantiate / material 超阈值才留栈
```

硬规则：

- 检测器**不得**读 replay 的 command type、action 序号、期望窗口；
- 动作标签只允许执行器使用，用于回放，不用于采样决策；
- 窗口统一为 `EvidenceWindow{trigger_id, reason, frame_range, sources, coverage}`；
- 触发源只能是数据异常，不是“命令类型”；
- 超预算自动降级并标 `instrument_distorted`。

### 10.3b 静态采集（S 层，补充证据）

运行时采集看不到“代码/资产本身”，静态层补的是**结构和归属**，不是性能事实。

```text
S0 项目快照：文件清单、大小、哈希、包依赖、ProjectSettings 摘要（缓存键=snapshot_hash）
S1 代码索引：C# AST、符号表、方法体、调用点、
              new/GetComponent/Resources.Load/Instantiate/Renderer.material 访问点、
              静态调用图（保守，不做动态派发推断）
S2 资产索引：纹理（尺寸/格式/mipmap）、材质（shader/引用）、
              Prefab/场景（组件与资产引用）、音频、Addressables 条目
S3 配置索引：Quality/Graphics/URP/物理/输入/时间步长
```

用途：

- 把运行时调用栈符号映射到**文件/方法/行**；
- 解释“谁创建了它/谁引用了它”（材质、纹理、Prefab）；
- 给候选补“结构上可能”的线索，例如方法体里有每帧 `new`；
- 分析 Agent 请求补证时，提供源码片段、调用点、资产清单、配置。

#### 静态能力边界（必须显式返回）

| 问题 | 静态能给 | 静态不能给 |
|---|---|---|
| 这个方法在哪、谁调用 | ✅ 文件/行/调用点 | ❌ 运行时是否真的走到 |
| 方法里有没有分配 | ✅ 语法上有 `new` | ❌ 每帧分配多少 |
| 资产多大、什么格式 | ✅ 尺寸/格式/引用 | ❌ 运行时实际占用/峰值 |
| 材质被谁引用 | ✅ 静态引用图 | ❌ 运行时实例化了几个 |
| 加载是同步还是异步 | ✅ 代码模式 | ❌ 实际耗时、是否卡帧 |
| 是否热路径 | ❌ | ✅ 需要运行时证据 |

**硬规则**：静态证据只能做 `potential`/结构解释，不能单独支撑
`proximity`、`competitiveness`、`counterfactual` 这些运行时因子；
静态不能把 finding 变成 `confirmed`。

#### 证据请求协议（含静态）

```text
EvidenceRequest.kind ∈ {
  runtime_window | replay_window | callstack | alloc_profile |
  render_counters | loading_trace |
  source_slice | code_search | ast_callgraph |
  asset_inventory | reference_graph | settings
}
```

响应必须带：

```text
evidence_class: runtime | static
snapshot_hash          # 静态证据的缓存/失效依据
can_support[]          # 这组证据能支撑哪些因子
cannot_support[]       # 明确不能支撑什么
limits                 # 采样率/覆盖范围/静态推断的保守性
```

约束：

- 静态请求按 `snapshot_hash` 缓存，工程变更即失效；
- 静态补采不重复烧运行时；运行时补采受轮次/预算限制；
- 分析 Agent 不得把静态结果当运行时结论；
- 请求不可满足时返回 `unavailable`，不允许脑补。

### 10.4 候选与定位

- 候选必须带 `source_kind`（function/alloc/render/load/asset）与证据指针；
- 每个源至少保留 K 条，禁止被 TopN 分数饿死；
- 定位用异常窗口 vs 正常窗口的统计对比（调用栈频率、分配点、渲染计数），不靠 action；
- 没有统计显著性的，标 `insufficient_evidence`，不硬报。

### 10.5 评测口径

| 类别 | 记法 |
|---|---|
| 命中标签 | TP |
| 有证据但不在标签集 | extra（不是 FP） |
| 声称越界但数据不支持 | unsupported |
| 未命中的标签 | FN |
| 标签不完整 | precision=unmeasured |

必做消融：

```text
A. 检测器可见 action 类型
B. 检测器完全不可见
B 的 recall 不得明显低于 A；否则说明依赖考试结构。
```

### 10.5b 标签入库（唯一通道：归纳总结 Agent 提议 + 用户 UI 批准）

**唯一允许的入库路径**，没有第二条。

```text
归纳总结 Agent（Summarizer/Knowledge）
  1. 汇总本次 run 的诊断、修复、复验结果
  2. 先用「机制 + 锚点 + 范围」查标签库
  3. 已存在 → 只做关联，不重复提议
  4. 不存在 → 生成 LabelProposal（status=proposed）
     附：证据指针、run_id、机制、锚点、帧范围、置信度、理由
  5. 不自动激活，不自动批准

用户（UI）
  6. 标签审核页看到待审队列
  7. 逐条「批准 / 驳回」，可填理由
  8. 批准 → status=approved，才进入标签库
  9. 驳回 → status=rejected，记录理由，不自动重提
```

硬规则：

- 工具与 Agent **不得自动批准**；
- `proposed` / `rejected` **不得**用于评测、训练打分或能力结论；
- 只有 `approved` 标签才算标签；
- 每次状态变更留痕：谁、何时、依据哪次 run、理由；
- 标签按 `project_id` 隔离；跨项目复用必须显式复制并重新批准；
- **oracle 标签不进产品标签库**：考试评分继续用封存的 oracle，两者物理分离，避免“考试答案变成产品标签”。

建议 schema：

```text
LabelProposal {
  label_id, project_id, run_id,
  mechanism, anchor{file, method, line},
  frame_range, metric, threshold,
  evidence_refs[], confidence, rationale,
  source: summarizer,
  status: proposed | approved | rejected | retracted,
  proposed_by, proposed_at,
  reviewed_by, reviewed_at, decision_reason,
  version
}
```

去重键：

```text
(project_id, mechanism, anchor.file, anchor.method, frame_bucket)
```

UI 要求：

- 待审列表默认按置信度/证据强度排序；
- 每条必须能展开证据（窗口、指标、调用栈、修复记录）；
- 批准/驳回需要用户明确操作，不能用默认值或批量自动通过；
- 驳回理由进入审计，供后续改进提议质量。

验收：

- 已有标签不重复提议；
- 未批准标签不参与任何评分/训练；
- 驳回后不会自动重提；
- 批准后才可被检索/评测引用；
- oracle 与产品标签库互不读写。

### 10.6 常驻保护

- 默认路径不变；只有证据不足/编译失败/修复后复发才进 loop；
- resident 最多 1 次，无 replay、无 verified；
- 所有失败可回滚，最终工程必须可用；
- 深档/钩子受预算，超限降级并如实标注。

### 10.7 风险

- 采集开销上升 → 分层 + 预算 + 降级；
- 环缓冲采样偏差 → 分配栈采样率可调 + 覆盖统计；
- 多轮重试成本 → 停滞/预算/无新假设三道闸；
- 标签不完整 → 只报标签 recall + 证据审计，不编 FP；
- 检测器误用 action → 代码层隔离 + 消融测试。

### 10.8 非目标

- 不写案例正则、不按 action 分支、不针对 11 个病例调参；
- 不要求健康对照、不把 extra 当 FP；
- 不把 resident 改成多轮自动修复；
- 不为通过考试放宽 verified。

## 11. I13：两遍 replay（r + r′）与缺失类证据

> 修正：r′ **完整执行整条 replay**，只在指定窗口开深档/分配栈；不剪命令，避免前后依赖导致不可复现。
> 决策不转人工：每场固定最多 3 个窗口，选不出就只做轻采。

### 11.1 两遍结构

```text
r  ：完整 replay，轻采（L0/L1 + marker），产出异常窗口/候选
决策：确定性打分 + LLM 排序，固定最多 3 个窗口
r′ ：完整 replay，同协议/同种子；仅在选中窗口（含余量）开深档/分配栈
```

关键约束：

- **r′ 不剪命令**：从头跑到尾，保证状态依赖；
- **测量是子集**：只采窗口内深档，窗口外保持轻采/关闭；
- **窗口有余量**：窗口前后各留 `margin`（建议 10–15 帧），分析只用核心窗口；
- **对齐靠事件/标记**，不靠绝对帧号：深档会改变帧时序，允许 ±N 帧漂移；
- **r′ 的耗时不能用于性能判定**：深档本身改变帧时间，只取调用栈/分配/加载证据；
- 同一协议指纹、同场景、同画质、同种子；不一致则 r′ 作废。

### 11.2 窗口决策（不转人工）

确定性打分：

```text
severity（越界幅度/持续帧数）
+ coverage_gap（哪个证据源还没候选）
+ diversity（不同机制优先）
- duplicate（同 metric/邻近窗口去重）
```

LLM 只做排序/理由，不新增窗口；**每场最多 3 个**；不足 3 个就少采；选不出就只保留 r。  
只有权限/安全（写工程、改感知层）才转人工；窗口不可复现 → `unavailable`，不转人工。

### 11.3 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **I13a 两遍骨架** | r 记录窗口；r′ 完整重放 + 窗口开关深档；余量；证据合并 | r′ 命令序列与 r 完全一致；只采窗口；窗口漂移可检测 |
| **I13b 缺失类证据** | 分配调用栈、加载 trace、材质/纹理/粒子计数、静态资产关联 | 5 类中至少 3 类能拿到窗口内证据；无证据明确 unavailable |
| **I13c 决策与预算** | 最多 3 窗口、打分/去重、LLM 只排序、无人工兜底 | 选窗有理由；超限截断；无窗口时不硬采 |
| **I13d 对比考试** | 同一考卷 one-pass vs two-pass：recall、证据量、成本 | recall 不降或升；无虚假 verified；成本可解释 |

### 11.4 风险

- 深档开销改变帧时序 → 用事件对齐 + 容差，不用绝对帧；
- r′ 完整重放成本高 → 最多 3 窗口，窗口外关闭深档；
- 窗口在 r′ 中偏移/消失 → 标 unavailable，不硬报；
- 多次 r′ 之间状态污染 → 每次 reset 到同起点；
- 深档数据不能当性能数字 → 只做解释证据。

### 11.5 非目标

- 不剪 replay 命令；
- 不因为窗口选不出就转人工；
- 不用 r′ 的耗时判性能；
- 不在被测工程注入监控代码（修复补丁除外）。

## 12. I15：定因证据、因果结构与伪优化门禁

> 目标：修掉“unclear 过线”“失败叠加补丁”“只把 1000 改成 10”的三类问题。
> 原则：**证据不足不许下结论；失败不许保留；结构不对不算修复；站点不全覆盖不算完成。**

### 12.1 因果结构：OR / AND / ONE

```text
OR   互斥备选：A 或 B，修一个应好
AND  多因并存：A 和 B 都贡献，必须都修
ONE  一个原因多个站点：同一机制出现在多处，必须全改
```

诊断输出 `CausalModel`：

```text
CausalModel {
  issue_id
  relation: OR | AND | ONE
  factors[]: {
    mechanism, sites[], mechanism_class,
    expected_invariant, evidence
  }
}
```

判定：

- 默认 `OR`；
- 升级 `AND` 需：每个因子 explains_share 有正证据、站点/调用栈不重叠、修 A 后指标部分改善但目标仍在；
- `ONE` 需静态/运行时站点清单完整；
- 无证据不得 `AND`。

### 12.2 执行协议

| 关系 | 协议 |
|---|---|
| OR | 每次从干净快照开始；失败（needs_recheck）→ 回滚 → 试下一个 |
| AND | A 保留（已验证）；B 在 A 上应用；验证 A+B；B 失败只回滚 B |
| ONE | 一个 plan 覆盖全部站点；未覆盖 → `partial_fix` |

硬规则：

- 默认互斥：验证失败必须回滚，不允许叠加未验证补丁；
- 验证必须覆盖 `attempted_targets` 全集，不只当前 hypothesis；
- 收尾时未 `verified` 的补丁全部回滚；
- 每次 attempt 记录：relation、sites、targets、snapshot、verdict。

### 12.3 伪优化门禁

机制分类：

```text
necessary_per_frame | init_only | event_driven | cacheable
```

规划字段：

```text
structural: bool
sites_covered[]
invariant
```

拒绝规则：

- `init_only/event_driven/cacheable` 的问题，补丁只改常量/循环次数/频率 → 拒绝；
- 必须出现结构变化：移到初始化、缓存、池化、事件驱动、删除调用；
- 必须覆盖该机制全部站点，否则 `partial_fix`；
- 典型反例：每帧 `new` 1000 → 10，不算修复。

### 12.4 验证：多帧稳态 + 站点剩余

验证输出：

```text
Verification {
  target_gone, new_clusters, guards_ok,
  per_frame_counts, count_slope,
  sites_remaining, pseudo_fix_suspected,
  status: verified | partial_fix | needs_recheck | observed
}
```

判据：

- `target_gone` + 无新 cluster + 守护不劣化；
- 目标指标改善超过 `min_delta/k·σ`；
- `init_only`：per-frame 创建/分配 = 0；
- `event_driven`：事件外创建/分配 = 0；
- `sites_remaining = 0`；
- 任一不满足 → 不得 `verified`。

### 12.7 风险

- AND 判定过松 → 补丁叠加；必须“部分改善 + 独立证据”双条件；
- 站点清单漏动态创建 → 静态为主、运行时补；漏站标 `sites_unknown`；
- 多帧计数开销 → 只用通用计数器，窗口有限；
- 伪优化误杀合法限流 → 要求 `mechanism_class=necessary_per_frame` 才允许调频；
- 回滚复杂度 → 每 attempt 快照，禁止跨 attempt 复用脏状态。


### 15.2 核心变化

```text
不再：N 个 finding → N 个病例循环 → N 次 capture
改为：N 个 finding → M 个机制单元 → M 个补丁 → 1 次 capture 验全部
```

一次 replay 覆盖所有病例；capture 是“整场回放”，不是“单病例回放”。

### 15.3 流程

#### 第 0 步：基线

```text
3 次 replay baseline
记录 cluster / 指标 / 站点
```

#### 第 1 步：机制合并

```text
Finding[] → RepairUnit[]
```

合并键：

```text
mechanism + 站点集合 + 调用链根
```

一个 `RepairUnit`：

```text
unit_id
mechanism
targets[]        # 覆盖哪些 finding
sites[]          # 全部代码/资产站点
mechanism_class  # init_only / event_driven / cacheable / necessary
expected_invariant
```

要求：

```text
同机制、同站点的多个 finding → 合并
一个单元覆盖多个 target
一个单元可以包含多个 diff
```

#### 第 2 步：生成补丁

```text
M 个 RepairUnit → M 个 Patch
```

每个 patch：

```text
unit_id
diffs[]
sites_covered[]
expected_effect
structural: bool
```

#### 第 3 步：冲突分组

```text
同文件 / 同方法 / hunk 重叠 / 语义依赖
```

- 可合并 → 合并成一个 patch；
- 不可合并 → 拆成独立 group。

每个 group 后续一次 apply/compile/capture。

#### 第 4 步：批量应用 + 编译一次

```text
snapshot S0
apply patch_1 → S1
apply patch_2 → S2
...
compile once
```

编译失败：

```text
二分定位坏 patch
回滚它
重新编译
```

不逐 patch 编译。

#### 第 5 步：一次 replay 验全部

一次 capture 输出：

```text
每个 target：gone / metric_delta
全局：new_clusters / guards
```

结果：

```text
patch_i verified → 保留
patch_i failed   → 回滚
co-fix           → 记录，不单独归因
```

#### 第 6 步：失败分组定位（仅异常）

如果失败原因不明确：

```text
只对失败子集做二分/分组 capture
```

成本：

```text
1 + log(k) 次，不是 k 次
```

#### 第 7 步：下一轮只修失败目标

```text
failed_targets + history(diff/verdict/sites)
→ 换候选 / 组合修复
→ 新 batch
```

最多 R 轮，R 由用户配置。

#### 第 8 步：收尾

```text
未 verified 的 patch 全部回滚
记录 round history
```

### 15.4 数据契约

```text
RepairUnit {

}

Patch {
  unit_id, diffs[], sites_covered[],

}

}
```

### 17.3 四个接口

#### ProjectAdapter

```python
class ProjectAdapter(Protocol):
    def describe(self) -> ProjectSpec: ...
    def run_replay(self, replay: Replay) -> list[dict]: ...
    def capture(self, metrics: list[str]) -> dict: ...
    def compile(self) -> CompileResult: ...
```

`Command` 是项目自定义命令：

```python

```

UPI 不解释命令语义；DevSim 的 `Debug*` 只是 adapter 实现，不进入 core。

```json
{"metrics":[

]}
```

```text
LLM 输出 metric + invariant{file,method,pattern,expect}
verifier 只执行声明
pattern 必须命中 find，method 必须存在
```

#### Orchestrator

```text
Observe → Cluster → Diagnose → Ticket → Plan → Apply → Compile → Verify → Review → Record
```

LLM 负责路由与语义：

```text
证据够不够、先修哪个、是否需要人、失败后换假设还是停
```

```text
采样、阈值、编译、回滚、verified 判定、权限
```

## 18. I22：清障与反作弊

> 目标：让 UPI 只能通过“观察 + 证据 + 实验”得出结论，  
> 不能通过 fixture 名称、case 列表、oracle 或静态白名单绕开分析。  
> 原则：清障先于赋能。

### 18.1 目标

```text
1. Agent / bench / scorer 职责隔离
2. 移除产品路径上的 case 级入口
3. 审计并移除 fixture 特征
4. 用反作弊实验证明：删 action / 移 bug / clean / rename 都会改变结果
5. 任何“自主”声明必须能通过反作弊门禁
```

非目标：

```text
不在本迭代增加资源/配置修复能力
不为通过反作弊改检测阈值
```

### 18.2 职责隔离

拆成三层：

```text
upi/agents/...       产品 Agent：检测、定因、规划、执行、验证
bench/runner.py      考试驱动：只跑 replay、采集、落盘
bench/scorer.py      评分：只读 oracle，不参与决策
```

硬规则：

```text
Agent 进程不能读 paper.json / oracle
scorer 不参与检测、定因、修复
runner 不向 Agent 传 case_id / 期望答案
```

验收：

```text
审计 Agent 运行环境，paper.json 不可读
代码扫描：产品路径不 import bench/scorer
日志/trace 不出现 case_id / oracle 字段
```

### 18.3 移除 case 级入口

以下只允许存在于 bench：

```text
--targets
--max-units
--static-repair
paper.json
test_project 固定 replay
holdout 类名映射
```

产品入口只接受：

```text
项目 + replay 指令 + 指标配置
```

### 18.4 fixture 特征审计

逐项审计：

```text
probe/upi_evidence_v1.cs
  热方法白名单 → 必须改为从 profiler/callstack 采样推导
probe/marker/evidence
  按 ChromaGame/BoardModel 名称过滤 → 改为指标/调用栈
mechanism_inventory
  固定模式 → 移入 adapter/plugin，只作 potential
structural_playbooks
  固定模板 → 移入 adapter，不进入核心
replay_exec
  固定 action 语义 → ProjectAdapter 自定义命令
target_metrics
  固定别名 → MetricRegistry 配置
prompt / candidate card
  test_project 字样、固定方法名 → 泄漏审计
```

### 18.5 反作弊实验

独立目录 `bench/anti_cheat/`：

#### A. Action ablation

```text
删掉 replay 中一个 action
对应 finding 应消失或显著减少
```

#### B. Bug relocation

```text
把同一缺陷从 A 方法移到 B 方法
机制不变、锚点变
检测应跟随新锚点
```

#### C. Clean project

```text
无缺陷项目
findings 应接近 0
```

#### D. Distractor

```text
加入相似但不热的函数
不得全部报成 issue
```

#### E. Oracle isolation

```text
Agent 环境不可读 paper.json
```

#### F. Prompt leak

```text
候选卡、源码片段、日志不出现 case_id / 期望答案
```

#### G. 二次 holdout

```text
不同品类/不同目录结构
不是同一份代码改名
```

### 18.6 验收门禁

```text
ablation 响应正确
clean 误报接近 0
relocation 跟随新锚点
oracle 不可读
holdout 不是同项目改名
```

以上未过，不把“自主/泛化”写进能力声明。

### 18.7 风险

```text
1. 去掉热方法白名单后检出率下降
   → 先补采样推导，再删白名单
2. clean 工程仍报 potential
   → potential 与 issue 分账
3. 反作弊实验本身需要独立 oracle
   → 不让 Agent 接触
```

### 20.1 目标

```text
1. verified 必须等于：target 消失 + metric 达标 + 守护/感知通过
2. invariant 只能作为必要条件，不能单独判 verified
3. 每个 patch 单独做 per-target 反事实
4. 批量只用于“已验证有效、相互独立”的 patch
5. 明确定义“坏”：硬坏 / 超预算 / 不划算
6. 用新口径重跑 C2，接受 verified 数量下降
```

非目标：

```text
不通过放宽阈值提高 verified
不把 partial 改叫 verified
不用批量结果替每个补丁背书
不在新口径跑通前上 11case
```

### 20.2 数据契约：RepairContract

每个 unit 必须声明：

```text
primary_metric        # frame_time / gc_alloc / memory / drawcalls / load_time
min_improve           # 相对改善下限，如 5%
expected_effect       # 预期方向与量级
target_cluster        # 机制级 target，不是函数名本身
target_window         # 哪个动作/时间窗
guards[]              # 守护指标
guard_budget          # 每个守护指标允许退化
tradeoff_policy       # 允许什么换什么、汇率
perception_risk       # none / semi / blocked
```

### 20.3 状态语义

```text
verified
  target 消失
  primary_metric 改善 ≥ min_improve 且超过噪声
  所有 guard 不超预算
  无新 cluster
  perception 通过

verified_with_tradeoff
  primary_metric 改善
  某个 guard 变差但未超硬预算
  net_benefit > 0
  需要显式批准

partial
  target 未消失，或 primary 改善不显著，或站点未清

regressed
  guard 超预算，或新 cluster，或 perception 失败

unmeasured
  指标/窗口不可用

needs_recheck
  基线不足、声明不可执行、证据不足
```

### 20.4 “坏”的量化

```text
硬坏：
  compile 失败
  target 未消失且无解释
  新 cluster
  perception 失败
  回滚失败

超预算：
  guard_regress > guard_budget

不划算：
  net_benefit <= 0
```

### 20.5 合算性公式

```text
benefit = primary_improve / primary_budget
cost = Σ max(0, guard_regress / guard_budget)
net = benefit - cost
```

或空间换时间：

```text
allowed_guard_cost = exchange_rate * frame_saved
net = frame_saved - allowed_guard_cost
```

例：

```text
8 MB/ms
内存 +12MB，frame -3ms
cost = 1.5ms
net = +1.5ms → 合算

内存 +40MB，frame -1ms
cost = 5ms
net = -4ms → 不合算
```

`exchange_rate` 按平台/项目配置，不写全局常量。

### 20.6 单补丁反事实

```text

```

规则：


### 20.14 压缩 replay 可靠性验证

> 已把 `paper_replay.json` 的 wait 从 25.5s 压到 9.0s。  
> 单次实测 11 findings 保持，但一次不够。必须把“压缩 replay 可靠性”作为 I24 任务。

#### 目标

```text
压缩 wait 后：
  replay 仍能完成全部动作
  11 个 target 仍稳定检出
  不引入新 finding
  metric 分布不发生漂移
```

#### 对照

```text
paper_replay_fullwait.json  原版
paper_replay_shortwait.json 压缩版
```

#### 协议

```text
同一项目、同一场景、同一 target-windows 模式
每版各跑 N=5 次
不应用补丁
记录每次的：
  - replay 是否完整结束
  - candidates 数量
  - root 集合
  - 每个 target 的检出次数
  - 目标动作是否执行
  - counters 中位数
```

#### 验收

```text
1. 每个 root 在 shortwait 的 5/5 次都出现
2. shortwait 与 fullwait 的 root 集合一致
3. 不出现 fullwait 没有的新 root
4. candidates 数量波动不超过 ±1
5. 关键 metric 中位数差异在噪声带内
6. 任一 target 缺失 → 恢复该动作的 wait，不强行压
```

#### 失败处理

```text
如果某个 target 只在 fullwait 出现：
  只回退与该动作相关的 wait
  不整体回退
  记录动作 → target 的依赖
```

#### 输出

```text
runs/_probe/replay_reliability.json
  fullwait: runs/root 检出矩阵
  shortwait: runs/root 检出矩阵
  missing_roots
  new_roots
  candidate_counts
```

#### 何时做

```text
在修 verified 语义之前先做
否则无法区分：
  “压缩 replay 导致漏检”
  “verified 语义错误”
```

#### 风险

```text
1. 动画/结算需要时间，压缩过头会漏 target
2. 单次通过不代表稳定
3. replay hash 变化后旧 run 不可直接对比
```

## 21. I25：修复状态树、预算、黑名单与 UI

> 触发：I24 只解决“单次 verified 语义”，没有解决“多轮修复失败后怎么办”。  
> 当前：partial 直接回 B0，没有 checkpoint；没有按 finding 的 N 次失败；没有黑名单；UI 没有对应入口。

### 21.1 目标

```text
1. 修复-验证循环从“线性重来”改为“状态树 + 回退父 checkpoint”
2. 有显著改善但未达目标 → 保留，标 improved_partial
3. 连续 N 次实质失败 → 回退父状态；根状态失败 → finding failed
4. 每一层都有硬预算，防止指数膨胀
5. 建立 finding 黑名单指纹库，人工管理、TTL、可清理
6. 真实工况只报绝对 delta；考试 coverage/force 仅用于 bench
7. UI 必须提供：状态树、attempt 时间线、预算、黑名单、模式隔离
```

非目标：

```text
不用黑名单影响考试评分
不用 clean 参考指导真实工况
不用函数名/站点数替代性能改善
不在预算内无界搜索
```

### 21.2 真实工况 vs 考试

#### 真实工况 production

```text
没有 clean
每个 finding 都是潜在优化点
开工单前评估原因、可修复程度、预期效果
修复后只看同一 finding、同一窗口的绝对 delta
有显著改善就保留
无改善/变差/新问题 → 回滚当前 patch
```

#### 考试 exam

```text
0case + 同一 replay = clean 参考
coverage = (N - M) / N
force = (before - after) / headroom
headroom = before - clean_ref
```

约束：

```text
coverage/force 只出现在 bench
不进入生产 repair 决策
考试不查黑名单
```

### 21.3 状态树模型

```text
RepairState
  state_id
  parent_state_id
  project_id
  finding_fingerprint
  git_ref / asset_hash / scene_guid
  metric_before
  findings_before
  accepted_patch_id
  status: active | best | abandoned | failed | verified
  depth
  attempts_at_state
  created_at
```

```text
RepairAttempt
  attempt_id
  state_id
  patch_id
  candidate_id
  snapshot_ref
  compile_ok
  capture_ref
  delta
  guard_delta
  new_findings
  perception
  status:
    improved_partial | verified | no_effect | regressed | infra_failure
  cost: captures/tokens/wallclock
```

规则：

```text
improved_partial → 创建子状态，保留
verified         → 创建子状态，记成功
no_effect        → 回滚当前 patch，attempts_at_state += 1
regressed        → 回滚当前 patch，attempts_at_state += 1
infra_failure    → 不扣 finding 配额，重试/转人工
```

### 21.4 搜索与回退

```text
DFS，默认单链
失败 N 次当前状态 → 回退 parent
parent 仍失败 N 次 → 继续上退
到根 baseline 仍失败 N 次 → finding failed
分叉只用于停滞/冲突/剩余空间大
```

配置：

```text
max_attempts_per_finding
max_attempts_per_state
max_branches
max_depth
max_total_attempts
max_captures
max_wallclock_s
max_tokens
```

默认建议：

```text
max_attempts_per_finding = 6
max_attempts_per_state = 2
max_branches = 2
max_depth = 2
max_total_attempts = 12
```

指数约束：

```text
节点上界 = 1 + B + B² + ... + B^D
实际 attempt 再受 max_total_attempts / 墙钟 / token 硬截断
```

剪枝：

```text
state_hash 去重
patch_fingerprint 去重
连续无显著改善 → 停止当前分支
当前最佳已接近理论上限 → 停止
分支数达上限 → 只走最佳
```

### 21.5 黑名单指纹库

#### 目的

```text
确认在预算内无法达成目标的 finding 窗口
后续生产优化跳过，避免反复烧采集/LLM
人工可清理，定期重试
```

#### 指纹

禁止只用类名/函数名。

```text
BlacklistFingerprint
  signature           # 机制级 finding signature
  window              # 动作窗口，如 open_shop
  metric              # gc_alloc/frame_time/...
  protocol_fingerprint# replay/scene/quality/tier
  project_scope       # project_id / profile
```

#### 记录

```text
BlacklistEntry
  fingerprint_id
  signature
  window
  metric
  protocol_fingerprint
  project_scope
  reason
  attempts
  last_seen
  owner
  ttl
  status: proposed | active | expired | retired
  audit[]
```

#### 规则

```text
命中 active → 规划前 skip，记录 blacklisted
自动只生成 proposed，不自动永久 active
人工批准后 active
TTL 到期 → expired，重新允许尝试
代码/replay/协议变更 → 指纹失效
黑名单不进入考试，不影响 N/M
```

## 22. I25-ext：把 I25 装进主流程，打通完整考试

>
> 边界：  
> “完整考试” = 端到端跑完并有真实产物，不等于“全部 verified”。  
> 是否通过由指标判定；如果仍是 0 verified，必须如实报告，不能改口径。

### 22.1 当前缺口


### 22.2 目标架构

```text

  detect
  diagnose
  plan
  fix/verify
    └─ RepairEngine (repair_serial)

         attempt 2 → ...
         返回 tree + 结果
  review
  record
```

```text

  单 finding 尝试

  只保留决策函数（Observation/decide_next）
  不再承担执行循环
```

硬边界：

```text
预算：orchestrator 传剩余预算，engine 只花子预算
回滚：单 patch/checkpoint 只在 engine
工单/报告：只在 orchestrator
```
