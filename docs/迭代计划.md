# UPI 迭代计划（v2：两形态 + 探针优先 + UI 唯一通道）

> 状态：**执行中**。最后更新：2026-11-12（I7 方向修正；I7b 优先）。
> 本文是后续开发的单一路线图；与旧 DESIGN/AGENTS 冲突时，以本文 + 对应 ADR 为准。
> ADR：`docs/adr/0001`~`0005`。

## 0. 目标形态

一个本地常驻的 Unity 性能 Agent：

> **一个探针、两种形态（常驻 / 回归）、一套事件-聚类-指纹-修复核心；所有人类操作只通过本地 Web 控制台完成，CLI 只保留启动、诊断和应急。**

### 两种形态

| 维度 | 常驻形态（日常开发） | 回归形态（批量回归） |
|---|---|---|
| 数据源 | 常驻探针 + 1Hz 哨兵/抽检 | 确定性 replay + 测试目标 |
| 问题定义 | 预算线 / 相对基线 / 抽检异常 | replay 指令 + 测试目标 |
| 复现 | 不要求 3 次基线 | 3 次（或 N 次）基线 + 聚类 + 复现率 |
| 修复 | best-effort，编译/冒烟/可回滚 | 修 + 同 replay 重跑 + 重新聚类 |
| 结论 | `unverified`，不进成功率分母 | `verified`，进成功率 |
| 节奏 | 常驻 / 实时 | 批量 / 夜间 / CI / 里程碑 |

**硬规则**：常驻不得记 `resolved/verified`；回归的 `verified` 必须来自“同 replay、同 cluster 消失、无新 cluster、守护不劣化”。

## 1. 五条架构定调

1. **单探针**：合并两个注入件，一个回调、一个心跳、一条事件流；用户三态开关（关/稳态/全程）。1Hz 轮询只做哨兵。
2. **事件两类**：`breach`（确定越界，进修复循环）、`sample`（不确定抽检，只产候选）。
3. **cluster 是单位**：一个 replay/巡检里多个相同/不同问题先聚类再分类；修复和验证都以 cluster 为单位。
4. **批量工单、串行落地**：工单可列多个候选，按置信度排序；一次只落一个 patch，每步 snapshot → 编译/冒烟 → 观测 → keep/rollback → 下一个。
5. **UI 唯一通道**：本地 Web 控制台；文件只作审计载体；CLI 只启动/诊断/应急。

## 2. 数据与验证等级

```text
ProbeEvent(kind=breach|sample, frame, metric, value, series/ring, a4, protocol_fp)
IssueCluster(cluster_id, metrics, rel_range, shape, occurrences, reproduction_rate)
Fingerprint(features, pattern_id, root_cause, playbook_id, confidence, stats)
BatchTicket(id, mode, items[], status)
PatchAttempt(ticket_id, patch, snapshot, safety, observation, decision)
Verdict(mode, verification=unverified|observed|verified|failed, target, guards, new_clusters)
```

统计必须分账：`mode ∈ resident|regression`、`verification_status ∈ unverified|observed|verified`。

### 3.1 I7 方向修正（权威）

- **产品目标**：不是“修好人为植入缺陷”，而是“找到相对可达参考值得做、做得到、
  可验证的优化机会”。`Issue`（越界/回归）与 `Opportunity`（无越界但有差距）分账。
- **CLEAN 退出产品**：不再当目标/负对照；噪声来自同场景重复运行，合格线来自
  floor/budget，机会参考来自 peer/history/static/algorithmic；`zero-to-zero=unassessed`。
- **去夹具化**：`_refs`/`defect_ref`/`fix_subject`/按行切片只允许测试；
  产品 planner 从当前源码+证据生成 diff，不得按 `profile_id` 分流。
- **工程选择**：修复对象必须在 UI 中选；保留最近/收藏/校验/归档/历史；
  活动工程绑定所有操作，运行中禁止切换。
- **真实开发模拟工程**：`sim/project`（Chroma Rogue，三消+轻肉鸽）统一入口/默认场景
  + 18 常规 + 3 混合 + 3 负对照（共 24）；oracle/replay 由评估者持有，不进工程；
  replay 改为项目指令序列，UPI 工具执行，UPI 内 Agent 隔离；Addressables 24/24 已通，
  全包体 <30MB。当前 24 case 评测通过，I8 起按真实项目边界重构。
- **不保留兼容性**：工具尚无使用者/历史包袱；旧 `projects/*.json`、旧 API/CLI
  可直接替换，不做迁移层/双读/fallback；`ProjectRegistry` 是唯一事实源。
- **视觉/交互重设计**：主界面只保留「开始游戏 / 说明 / 专项测试下拉」；2.5D 色块、
  拖拽交换、消除/掉落动效、倒计时进度条、BONUS 可见化；详见 `docs/视觉设计.md`。
- **验收**：I7b 先做到“无 JSON 手编即可选择并恢复工程”；I7c/I7d 做到
  “无 clean 也能机会发现、未见工程可生成/拒绝”；I7e 不是只测 CPU；
  I7f 才是真实用户工程验收。

## 4. 验收

### 常驻形态
开探针 → 检出 breach/sample → 聚类 → 批量工单 → UI 批准 → 2+ patch 串行 → 一个失败回滚 → 全程 `unverified` 留痕。

### 回归形态
定义 replay + 测试目标 → 3 次基线 → cluster 矩阵 → 稳定 cluster → 修复 → 同 replay 验证 → `verified` 报告；失败可回滚。

### UI
所有人类操作在 UI 完成；不手工编辑 JSON/Markdown；CP936 正常；localhost 安全；关键流程有浏览器冒烟测试。

### 工程
旧测试保持绿；新增事件/聚类/指纹/执行器/UI API 测试；README/使用说明改为 UI 口径；旧 ANSI TUI 删除或标 deprecated。

### 工程选择/管理（I7b）
- 无 JSON 手编：UI 新增/选择/编辑/校验/归档工程；
- 最近工程与上次场景/质量档/模式自动恢复；
- 活动工程绑定所有探针/建单/执行/回归/报告，运行中禁止切换；
- 路径失效 fail-closed，不回退夹具；有历史 run 只允许归档，物理删除二次确认。

### 机会发现（I7c/I7d）
- 无 clean 也能产 `OpportunityFinding`（floor/budget/static/peer/history）；
- 无参考时 `insufficient_evidence`；无机会工程不硬造 plan；
- `Opportunity` 与 `Issue` 分章、分账，不混入 resolved/verified；
- 未见工程可从当前源码生成或明确拒绝，不依赖 `_refs`/profile-id。

### 8.4 LLM 主体后的链路（含容错与反馈）

```text
证据（测量）
→ LLM 诊断（六因子 + 根因候选 + 证据引用）
     ↳ 输出非法/超时/限流 → 重试/降级（见 8.5）→ 仍失败则 needs_human
→ LLM 规划（结构化补丁草案，或 insufficient_evidence）
     ↳ find 不唯一/不命中 → 把“实际源码片段 + 错误”回喂 LLM，最多 2 轮
     ↳ 编译失败 → 把编译器错误回喂 LLM，最多 2 轮
→ 确定性执行：快照 → 精确 apply → 编译 → 可运行冒烟 → 失败回滚
→ 复验：同 replay 前后 observed；满 3 基线才 verified
→ 写入本项目历史（供下次参考，不直接复用）
```

规划输出契约（新）：

```json
{"why": "...", "edits": [{"file": "Assets/...", "find": "...", "replace": "..."}]}
```

执行器只做三件事：精确命中校验、应用、编译；不猜意图、不做模板替换。

### 8.5 容错与反馈（硬要求）

| 失败点 | 处理 |
|---|---|
| 连通性/鉴权/模型不存在 | 熔断：不重试同类请求，标 `llm_unavailable`，转人工；记录原因 |
| 超时/限流/5xx | 按配置退避重试（默认 2 次）；仍失败 → 结构化失败，不阻塞后续候选 |
| 输出非 JSON / 缺字段 | 修复性重试 1 次（附错误）；仍失败 → 该候选作废并留痕，继续下一个 |
| tool call 不被支持/报错 | 降级为纯 JSON 输出；仍不支持 → 标 `tool_unsupported`，不重试 |
| 补丁 find 不命中/命中多次 | 回喂实际源码与错误，最多 2 轮；仍失败 → 记“未能规划”，转人工 |
| 编译失败 | 回喂编译错误，最多 2 轮；仍失败 → 回滚 + `compile_failed_rolled_back` |
| 任一轮次超预算 | 停止该 Issue，保留全部记录，转人工 |
| 进程崩溃/断线 | 每阶段落盘；resume 从最后完成阶段继续，不重复已花调用 |

通用规则：

- 每次 LLM 调用都记 token/耗时/重试/错误类型；
- 单个失败不得让整轮考试卡死或静默；最差结果是 `needs_human` + 原因；
- 重试有上限（默认 2），禁止无限循环；
- 提示词泄漏筛查 fail-closed（命中 test/oracle/case 等词直接拒发）。

## 9. I11：模式感知工作流（共享内核 + 能力表）

> 背景：I10 考试暴露了三个问题（编译失败会中断、证据不足无回路、修复后没有复验）；但考试项目有 replay、常驻项目没有。
> 原则：**共享内核，按 mode 给能力；绝不把考试口径套到常驻。**

### 9.1 两条形态的硬边界

| 维度 | resident | regression / 考试 |
|---|---|---|
| 可复现性 | 不保证 | replay 可复现、可对齐 |
| 证据来源 | live 窗口、源码、调用栈、历史 | 上述 + replay 指定帧/窗口 |
| 验证阶梯 | 编译 → 冒烟 → 观察（unverified） | 编译 → 冒烟 → replay 一次 → 3 基线（verified） |
| Agent loop | 事件触发，最多 1 次补证据/重规划 | 可多次，预算更大 |
| 允许结论 | `unverified` / `observed` | 才允许 `verified` |
| 自动落地 | 默认保守，写操作仍走权限闸 | 考试可由用户授权批单 |

### 9.2 共享内核（两模式复用）

- 快照、精确 apply、编译门禁、回滚、预算、trace；
- `EvidenceRequest` 协议与工具白名单；
- 最终可用性门禁：收尾必须可编译/可启动，否则整卷 0（但过程不停）；
- 单修复点失败 = 该点 0，不拖垮整卷（回滚成功的前提下）。

### 9.3 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| I11a | mode 进 state/工单/verdict；能力表（providers、ladder、budgets、auto_apply） | 两模式工具集不同；resident 拿不到 replay 工具 |
| I11b | 编译失败回路：错误回喂规划 ≤2 轮；仍失败回滚；继续下一个；退出时可用性门禁 | 注入编译错误：有界重试、回滚、工程可编译；单点失败不中断 |
| I11c | `EvidenceRequest` 双向链路：分析请求 → 检查定向补采 → delta；≤2 轮、去重、unavailable 不脑补 | 常驻只能 live 补采；回归可 replay 补采；请求不可满足时转人工 |

### 9.4 常驻模式保护（硬要求）

1. 默认路径不变：发现 → 保守修复 → 观察 → 不行回滚；
2. 只有“证据不足 / 编译失败 / 修复后仍复发”才进 loop，且最多 1 次；
3. 常驻工具表里没有 replay，代码层拒绝；
4. verdict 层强制：resident 不得写 `verified`；
5. 预算独立且更小；超预算转人工；
6. 任何失败必须可回滚；最终工程必须可用。

### 9.5 考试模式规则

- 一道题、多得分点；
- 编译失败：回喂重规划 ≤2 → 回滚 → 继续；最终不可用 = 0；
- 修复后先 replay 一次（目标 cluster 消失、无新 cluster），再决定是否跑 3 基线；
- 单次 replay 只作覆盖/回归门禁，不作统计结论；
- 用户授权代理批单；评分看 Agent 的判断与方案。

### 9.6 风险

- 常驻 loop 增加时延/成本 → 触发式 + 小预算；
- replay 单次仍可能偶然通过 → 不升 verified，3 基线后才升；
- 能力表配置漂移 → 单点定义，测试钉住；
- 编译回路与权限闸冲突 → 回喂规划不绕过审批，写入仍要批。

## 10. I12（修订版）：数据链接真 + 采集扩充

> 修订原因：上一版把“动作对齐/负对照”当成方法，违背“所有输入都是带病样本、检测不能预设动作”的前提。
> 本版原则：
> 1. **输入永远是带病样本**；真值只来自注入标签或专家确认，不需要健康对照；
> 2. **检测单元是数据异常，不是 action**；replay 只是负载，不向检测器暴露命令类型；
> 3. 不再要求“干净工程 FP=0”；precision 在标签不完整时标 `unmeasured`；
> 4. 常驻保守、回归可复现，两者共享内核、按 mode 给能力。

### 10.1 目标

| 目标 | 说明 |
|---|---|
| 数据链不再断 | 历史接项目库、证据回路接线、每次尝试都记账、停止原因可解释 |
| 采集覆盖全生命周期 | 常开轻量层 + 环缓冲 + 越界升级 + 通用钩子，不依赖已知动作 |
| 检测可盲测 | 不给 action 语义也能发现异常；给标签才算 recall |
| 评测不循环论证 | 标签召回 + 证据审计 + extra/false 分离；无健康对照要求 |

### 10.2 阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| **I12a 数据链修复** | ① 历史读写统一到 `runs/projects/<id>/knowledge`；② 考试/回归节点传 `mode` + `evidence_collector`；③ 每次尝试一条 RepairRecord；④ 停止原因落 findings | 连跑两场能读历史；证据请求真的执行；两次尝试 repairs=2；stop_reason 可查 |
| **I12b 采集扩充（盲采）** | 运行时 L0 每帧标量 + L1 环缓冲 + L2 越界升级 + L3 通用钩子；静态 S0 快照 + S1 代码索引 + S2 资产索引 + S3 配置索引 | 未知时刻注入越界，能拿到事前 ring 与事后调用栈；静态证据可按请求补采且标清边界；检测器不读 action 类型 |
| **I12c 异常驱动定位** | 越界判定（绝对门限/滚动基线/变化率/变点）；触发后冻结事前、升级事后；候选按“异常窗口 vs 正常窗口”统计对比排序 | 不依赖 action 也能产出候选；盲区清单显式 |
| **I12d 重试闭环** | `max_steps` 取能力表；`needs_recheck` 继续到 clean/budget/stagnant；失败换下一个 hypothesis；同目标+同 diff 连续两次停 | 假驱动：多轮都 recheck、换假设、停滞即停、原因可查 |
| **I12e 标签入库 + 评测契约** | 标签来自注入清单/专家；输出分 TP / extra / unsupported / FN；precision 无完整标签时 `unmeasured`；action 标签消融 | 隐藏 action 类型后 recall 不明显下降；extra 不记 FP |
| **I12f 报告与图表** | attempts、每轮 ladder、stop_reason、extra、盲区、开销 | 报告能答“为什么停、哪轮失败、漏在哪” |
| **I12g 白纸真考** | 清库 → 重出卷 → live 全链路 → 图表 | 能看到多轮 attempts、盲采证据、extra 分类；无虚报 verified |

顺序：I12a → I12b → I12c → I12d → I12e → I12f → I12g。
I12a 先修账；I12b/c 是检测能力主体；I12d 只修重试语义。

### 10.3 采集分层（I12b 细节）

```text
L0 常开：frame time / GC / drawCalls / batches / memory / loading / marker
L1 环缓冲：最近 N 帧标量 + 最近 marker，越界时冻结
L2 升级：触发后开深档 + 分配调用栈，采 M 帧后关
L3 钩子：Resources.Load / Instantiate / material 超阈值才留栈
```

硬规则：

- 检测器**不得**读 replay 的 command type、action 序号、期望窗口；
- 动作标签只允许执行器使用，用于回放，不用于采样决策；
- 窗口统一为 `EvidenceWindow{trigger_id, reason, frame_range, sources, coverage}`；
- 触发源只能是数据异常，不是“命令类型”；
- 超预算自动降级并标 `instrument_distorted`。

### 10.3b 静态采集（S 层，补充证据）

运行时采集看不到“代码/资产本身”，静态层补的是**结构和归属**，不是性能事实。

```text
S0 项目快照：文件清单、大小、哈希、包依赖、ProjectSettings 摘要（缓存键=snapshot_hash）
S1 代码索引：C# AST、符号表、方法体、调用点、
              new/GetComponent/Resources.Load/Instantiate/Renderer.material 访问点、
              静态调用图（保守，不做动态派发推断）
S2 资产索引：纹理（尺寸/格式/mipmap）、材质（shader/引用）、
              Prefab/场景（组件与资产引用）、音频、Addressables 条目
S3 配置索引：Quality/Graphics/URP/物理/输入/时间步长
```

用途：

- 把运行时调用栈符号映射到**文件/方法/行**；
- 解释“谁创建了它/谁引用了它”（材质、纹理、Prefab）；
- 给候选补“结构上可能”的线索，例如方法体里有每帧 `new`；
- 分析 Agent 请求补证时，提供源码片段、调用点、资产清单、配置。

#### 静态能力边界（必须显式返回）

| 问题 | 静态能给 | 静态不能给 |
|---|---|---|
| 这个方法在哪、谁调用 | ✅ 文件/行/调用点 | ❌ 运行时是否真的走到 |
| 方法里有没有分配 | ✅ 语法上有 `new` | ❌ 每帧分配多少 |
| 资产多大、什么格式 | ✅ 尺寸/格式/引用 | ❌ 运行时实际占用/峰值 |
| 材质被谁引用 | ✅ 静态引用图 | ❌ 运行时实例化了几个 |
| 加载是同步还是异步 | ✅ 代码模式 | ❌ 实际耗时、是否卡帧 |
| 是否热路径 | ❌ | ✅ 需要运行时证据 |

**硬规则**：静态证据只能做 `potential`/结构解释，不能单独支撑
`proximity`、`competitiveness`、`counterfactual` 这些运行时因子；
静态不能把 finding 变成 `confirmed`。

#### 证据请求协议（含静态）

```text
EvidenceRequest.kind ∈ {
  runtime_window | replay_window | callstack | alloc_profile |
  render_counters | loading_trace |
  source_slice | code_search | ast_callgraph |
  asset_inventory | reference_graph | settings
}
```

响应必须带：

```text
evidence_class: runtime | static
snapshot_hash          # 静态证据的缓存/失效依据
can_support[]          # 这组证据能支撑哪些因子
cannot_support[]       # 明确不能支撑什么
limits                 # 采样率/覆盖范围/静态推断的保守性
```

约束：

- 静态请求按 `snapshot_hash` 缓存，工程变更即失效；
- 静态补采不重复烧运行时；运行时补采受轮次/预算限制；
- 分析 Agent 不得把静态结果当运行时结论；
- 请求不可满足时返回 `unavailable`，不允许脑补。

### 10.4 候选与定位

- 候选必须带 `source_kind`（function/alloc/render/load/asset）与证据指针；
- 每个源至少保留 K 条，禁止被 TopN 分数饿死；
- 定位用异常窗口 vs 正常窗口的统计对比（调用栈频率、分配点、渲染计数），不靠 action；
- 没有统计显著性的，标 `insufficient_evidence`，不硬报。

### 10.5 评测口径

| 类别 | 记法 |
|---|---|
| 命中标签 | TP |
| 有证据但不在标签集 | extra（不是 FP） |
| 声称越界但数据不支持 | unsupported |
| 未命中的标签 | FN |
| 标签不完整 | precision=unmeasured |

必做消融：

```text
A. 检测器可见 action 类型
B. 检测器完全不可见
B 的 recall 不得明显低于 A；否则说明依赖考试结构。
```

### 10.5b 标签入库（唯一通道：归纳总结 Agent 提议 + 用户 UI 批准）

**唯一允许的入库路径**，没有第二条。

```text
归纳总结 Agent（Summarizer/Knowledge）
  1. 汇总本次 run 的诊断、修复、复验结果
  2. 先用「机制 + 锚点 + 范围」查标签库
  3. 已存在 → 只做关联，不重复提议
  4. 不存在 → 生成 LabelProposal（status=proposed）
     附：证据指针、run_id、机制、锚点、帧范围、置信度、理由
  5. 不自动激活，不自动批准

用户（UI）
  6. 标签审核页看到待审队列
  7. 逐条「批准 / 驳回」，可填理由
  8. 批准 → status=approved，才进入标签库
  9. 驳回 → status=rejected，记录理由，不自动重提
```

硬规则：

- 工具与 Agent **不得自动批准**；
- `proposed` / `rejected` **不得**用于评测、训练打分或能力结论；
- 只有 `approved` 标签才算标签；
- 每次状态变更留痕：谁、何时、依据哪次 run、理由；
- 标签按 `project_id` 隔离；跨项目复用必须显式复制并重新批准；
- **oracle 标签不进产品标签库**：考试评分继续用封存的 oracle，两者物理分离，避免“考试答案变成产品标签”。

建议 schema：

```text
LabelProposal {
  label_id, project_id, run_id,
  mechanism, anchor{file, method, line},
  frame_range, metric, threshold,
  evidence_refs[], confidence, rationale,
  source: summarizer,
  status: proposed | approved | rejected | retracted,
  proposed_by, proposed_at,
  reviewed_by, reviewed_at, decision_reason,
  version
}
```

去重键：

```text
(project_id, mechanism, anchor.file, anchor.method, frame_bucket)
```

UI 要求：

- 待审列表默认按置信度/证据强度排序；
- 每条必须能展开证据（窗口、指标、调用栈、修复记录）；
- 批准/驳回需要用户明确操作，不能用默认值或批量自动通过；
- 驳回理由进入审计，供后续改进提议质量。

验收：

- 已有标签不重复提议；
- 未批准标签不参与任何评分/训练；
- 驳回后不会自动重提；
- 批准后才可被检索/评测引用；
- oracle 与产品标签库互不读写。

### 10.6 常驻保护

- 默认路径不变；只有证据不足/编译失败/修复后复发才进 loop；
- resident 最多 1 次，无 replay、无 verified；
- 所有失败可回滚，最终工程必须可用；
- 深档/钩子受预算，超限降级并如实标注。

### 10.7 风险

- 采集开销上升 → 分层 + 预算 + 降级；
- 环缓冲采样偏差 → 分配栈采样率可调 + 覆盖统计；
- 多轮重试成本 → 停滞/预算/无新假设三道闸；
- 标签不完整 → 只报标签 recall + 证据审计，不编 FP；
- 检测器误用 action → 代码层隔离 + 消融测试。

### 10.8 非目标

- 不写案例正则、不按 action 分支、不针对 11 个病例调参；
- 不要求健康对照、不把 extra 当 FP；
- 不把 resident 改成多轮自动修复；
- 不为通过考试放宽 verified。
