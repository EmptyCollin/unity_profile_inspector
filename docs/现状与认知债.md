## 二、关键机制是怎么实现的

**1. 双源采集（被实跑逼出来的架构）**
- A 档 = 轮询内置 `diagnostics get_performance`，渲染计数（drawCalls/setPass/batches/triangles/vertices）的**唯一**来源，实测 ~1.05 次/秒。
- A2 档 = 注入常驻回调 + `ProfilerRecorder`，逐帧取 `GC Allocated In Frame`、内存、`Animator.ProcessAnimations`。
- 为什么必须两源：实测枚举 5023 个 recorder 句柄后发现渲染计数**不在 recorder 体系里**，用它构造会**静默返回 0 且不抛异常**；而 recorder 体系里的 GC/动画指标，轮询通路又给不出。两源按指标归属划界，同一指标禁止跨源混用。

**2. 文件控制协议（eval 沙箱的必然形状）**
每次 `script eval` 是新编译的临时程序集：静态字段不跨调用存活，但注册的回调**跨调用存活且无法从新 eval 卸载**。于是：控制走 `runs/_probe/a2_cmd.txt`（`start:<nonce>` / `stop`），数据走 `a2_frame.json`，Python 侧只轮询文件。

**3. 幂等 = 心跳文件新鲜度**
不能用静态 bool（新程序集读不到），也不能用 `SessionState`（它跨域重载存活、回调注册不跨，会留下"标记已装、实际无人采样"的死状态）。只认"心跳文件 3 秒内被写过"这一外部可观测判据。

**4. 帧门控 + 时间节流**
`EditorApplication.update` 实测 ~2100 次/秒 ≠ 帧率。采样按 `Time.frameCount` 变化写入；控制检查与心跳分别降到 10Hz / 1Hz——这一步把采样器自身开销从 175~205% 打到 0.46~1.83%。

**5. 噪声带 = 窗口间 σ**
§3 定义的是"同一协议重复采样的离散度"。每夹具采 4 个独立窗口（预热 8 次轮询 + 20 次轮询/窗口），σ 由**4 个窗口中位数之间**算出，而不是单窗口内部抖动。检测与阈值**同源于** `calibration/multiwin_full.json`，杜绝"旧数据 vs 新阈值"的跨协议比较。

**6. 阈值只能被标定出来（代码强制，非纸面规则）**
`Thresholds.threshold_source != "noise_calibration"` 直接构造失败；标定文件缺任一检测器指标，检测**中止**而非沿用注册表初值。检测端还自带 CLEAN 对自身的误报自检（当前 0/4）。

**7. 契约门禁已做成可执行校验**（六条负例实测全拦截）
手调阈值被拒 / 渲染指标指定 A2 源被拒 / 感知层 EditPlan 配 auto 被拒 / 签名含文件名类名被拒 / low_confidence 进修复循环被拒 / Verdict 缺全量守护被拒。

## 四、本轮踩到并已固化为文档/门禁的实测教训

1. 渲染计数不属于 recorder 体系，**构造成功 ≠ 名称有效**，不存在名称静默读 0。
2. 无头编辑器（`-batchmode -nographics`）渲染恒为 0，GPU 显示 `Null Device`（G16）。
3. 回调跨 eval 存活、静态字段不存活、旧回调卸不掉 ⇒ 清残留只能重启编辑器（幽灵回调本轮咬了三次）。
4. 域重载会销毁内存场景物体 ⇒ 每轮录制前必须编辑态重建。
5. `eval` 内 `Thread.Sleep` 阻塞主线程会让"帧不推进"成为测量假象。
6. 静止场景指标分布退化（唯一值/样本 <0.1 或 MAD=0）⇒ `k·σ` 判据失效，任何改动都"显著"（G17；小样本下比例规则永不触发，已补 MAD==0）。
7. 采样器自身会把开销与**分配量**写进被测量（观察者污染），必须标定 probe_overhead。
8. 命令名/参数名/包名一律运行时探测，不猜（I8）：`editor_play` 已改名、`ProfilerCategory` 是 struct 不能 `Enum.Parse`、`GCAllocRecorder` 名字不存在、包名是 `com.unity.performance.profile-analyzer`。
9. 编译门禁的正确判据是 `script recompile_status.errors`，不是控制台条目数（曾因此把一个真实语法错误放过一整轮）。
10. 指标要贴机制：动画缺陷绑"主线程帧时"被整帧 4ms 摊薄两轮未检出，换 `Animator.ProcessAnimations` 立即从 0 跳到 362µs——修指标不动阈值，才守得住 §8.1。
11. **Frame Debugger 程序侧不可取当帧渲染结构**：`GetFrameEvents()` 给的是 SetPass 分组行（行数恒等于同帧 setPassCalls），逐笔明细只在 GUI 重绘时由树控件构建，`GetFrameEventObject` 全空，resume 同刻缓冲清空；`enabled` 属性只读（无 setter）。①-⑫ 全套入口已试尽（DESIGN §12），别再重试。
12. **失焦即停帧**：`runInBackground` 每次域重载被重置回 False，窗口失焦时帧号不推进——这是"FD 定格世界"误判的真正来源，也是驱动器必须进 Play 强制压上它的原因。
13. **探针侧禁止吞异常**：本轮三次误诊（把事件对象当序号传入、负帧号取模越界、JSON 逗号错位）全部因为 `catch` 静默——失败必须原样落盘留痕（`flush-err` 一类），否则最该检出的样本反而静默丢失。
14. **静默丢样本=造数据**：pydantic 默认忽略多余字段，`rel`/`gc_ring_*` 在 jsonl 里有、契约里没有 → 被无声吃掉 → 下游 AttributeError。越界样本契约已加 `extra="forbid"`；每笔构造拒收必须进 stats 计数。
15. **常驻件不得越权覆盖仪器状态**：回放驱动器活着就每帧压 `targetFrameRate=60`，把验证窗自设的 uncapped 覆盖掉，F-CPU-01 缺陷态分配被 vsync 等待帧从 78KB 抬到 183KB——**被测机制淹死在仪器行为里**，修复效果直接测不出。现改为显式 `_armed` 门控（默认纯旁观），采样方采前 `disarm`。
16. **两束可比性要靠数据自证，不能靠人回忆**：`_instr_pre/_instr_mid` 记心跳与封顶形态，判定入口设三闸（束内漂移、两束形态、常驻件存活）；形态判据用窗口数据自身（capped60≈16.6ms/uncapped≈1.9ms，相差近十倍故 12ms 分界可靠）。第一轮彩排那种混比现在会被当场拦下。
17. **豁免必须有证据划范围，而且证据要覆盖所有比较侧**：曾按“只有 `monoUsedBytes` 响应强制 GC”划豁免范围（probe/gc_floor.cs），但更根本的错是**只采了改后态一侧**——单侧地板分不清“修复净代价”与“两侧都在攒垃圾”。现在两侧各采一份 fresh，post_gc 对 post_gc；拿不到任一侧即未评估盲区，不做豁免。
18. **自己提的机制假设，要允许自家实测否证它**：我曾推断"+10.5MB 是修复饿死 GC、编辑器观测垃圾积累造成的假象"，并为它设计了地板复核。实测结果是 GC 只压掉 2.8MB（118.5→115.7，仍远高于改前 104.7）——**假设至多解释 27%，主因是真实占用**。地板复核正确地拒绝豁免、维持 `regressed`，是机制按设计在工作，不是失败。教训：豁免逻辑必须等响应性实测出来才能定范围，先有假设就先去测它，别把推断当结论写进判定。 **同一条纪律的第二课**：被否证的其实是“单侧地板”这个设计——地板复核拒绝错误的豁免是对的，但它给出的替代解释（真实占用 +10MB）也是错的；正确答案要靠第三个实验（交替块）才浮出来。一个否证只够排除一个假设，不要顺手把否证结果当成新结论。
19. **彩排收尾用检出复位单文件而非 `reset --hard` 整树**：机制件（`upi/`、`scripts/`）与夹具在同仓库，整树回滚会把未提交的机制改动一起撤掉；且 dry-run 的"工作区干净"检查只看夹具路径，护不住机制件——**跑彩排前必须先提交机制改动**。
20. **文档自洽要实测回查**：AGENTS v0.6 头部声明了 G17 但正文一直没有这一行；DP-1 变更记录里写了不存在的"§4A"。写完立刻回查仓库实况，否则交接文档自己带债。
21. **窗口值不等于占用量**：`monoUsedBytes` 这类计数器答的是“此刻有多少还没回收”，不是“这段代码吃了多少”。回收时机一变（修复把高频小分配清零 → GC 触发变稀），窗口值就与真实净常驻脱钩——实测 7.82MB vs 1.94MB，差 4 倍。任何“占用类”结论必须先把回收钉到同一起点（强制 GC 后读），否则判定的是运行时调度器而不是代码。
22. **否证一个假设 ≠ 证实另一个**：交替块同时否证了“会话时长污染”（缺陷块漂移仅 0.69MB），剩下的 1.94MB 净代价仍属未定机制（量级与预生成数组/复用缓冲/缓存引用相符，但没做单变量确认）。文档只写“已定性到量级、未定论到机制”，不写“已解决”。
23. **采信闸过严 = 自废守护**：新口径首轮真彩排里，`monoUsedBytes` 被“pre_gc 必须≈同侧窗口中位（2%）”的交叉校验推进盲区——可 fresh 是**独立 Play 会话**（重开场景、重新进 Play、会话年龄不同），与验证窗束天然差 5~10%（当日实测 6.3%）。拿同会话容差去要求跨会话数据，等于把合法数据系统性判成不可信，守护形同虚设。现降级为 25% 粗防抖（只拦“来自别的机器状态”级异常），偏差值留档可回溯。**容差必须按数据的采集方式定，不能照搬另一路的数**。
24. **attempt 前基线必须在写入之前锁定**：状态机接线时我把 before 束采集放在verify 节点，而 verify 跑在 fix 之后——那时夹具已是修复态，采出来的“before”其实是第二个 after，两侧对比直接失真。这类错在直线式彩排脚本里不会暴露（步骤顺序写死），只有拆成状态机节点才浮出来。现由 fix 在 execute 前采 before 束与改前态 fresh，经 `pre_attempt` 传递给 verify。**引入回环结构时，要重新审视每一步对“此刻机器处于什么状态”的隐含假设**。
25. **判定口径要按「物理量」覆盖，不能按「指标名」覆盖**：同一个 Unity `Total Used Memory` 计数器有两条采样路径、两个名字（A 档轮询 `totalAllocatedBytes` / A2 逐帧 `total_used_per_frame`）。我实测确认前者不响应强制 GC（Δ0.005%）并登记为盲区，却漏了后者——它不在记忆体集合里，于是绕过 fresh 口径落到「窗口值 + 1% 容差」分支，被 192% 的跨会话自然波动（同一份缺陷代码 12 个会话实测极差 1.19GB~10.26GB）判成 +2.25% 劣化，连撞两轮假 regressed。集合表驱动的实现每次登记都要反问「这个物理量还有没有别的名字」。
26. **核验保留与否要用本次产物自己的标记，不能凭记忆挑关键词**：第三轮实测后用另一版修复的字段名去 grep 已保留的改动，得出「没保留」的错误结论；实况是 `verdict=resolved` 且 26+/22- 改动确实在位。核验前先读 EditPlan 的真实 diff 内容。
