# 设计审查：与“能力优先、不预设完美答案”相悖的残留（2026-11-13）

## 审查基准

从两条原则推导出的判据：

| # | 判据 |
|---|---|
| P1 | 不预设“完美优化版/干净工程”作为工具输入或基线 |
| P2 | 评测语义（CLEAN、holdout、fixture_spec）只用于评工具，不进产品运行路径 |
| P3 | 不用“匹配代码文本/正则/方法名”产生诊断结论或修复方案 |
| P4 | 不做跨机器阈值迁移；标定只量本机仪器/会话噪声 |
| P5 | 不用答案文件（`_refs`、`defect_ref`、按行切片）生成修复 |
| P6 | 产品默认不指向夹具工程、不依赖夹具命名 |
| P7 | 能力结论只来自运行证据；不知道就报不知道 |
| P8 | 夹具/留出集是评测资产，不是用户工程的前置条件 |

审查范围：`upi/`（76 文件）、`scripts/`、`probe/`、`knowledge/`、`baselines/`、`config/`；
`sim/`、`fixtures/` 只作为被引用方检查。方法是按主题 grep + 逐处读上下文，不是只看关键字。

---

## 结论

**P0（直接违反，产品路径）4 项；P1（结构性残留）6 项；P2（口径不一致/窄能力）5 项。**

---

## P0-1 诊断链仍是“夹具目录 + 代码正则”

**证据**

- `upi/agents/nodes.py:283`：`cands = retrieve_candidates(issue, det)`
- `upi/core/candidate_retrieval.py:65-73`：候选目录来自 `active_profile().subject_asset_dir(det.subject)`（夹具编号 → 目录）
- `upi/core/candidate_retrieval.py:25-59`：`PATTERNS` 是 10 条正则 → 根因模板
- `upi/core/candidate_retrieval.py:113`：命中行还必须落在 `Update/Start` 之后

**为什么违反**

真实工程没有 `F-CPU-01` 这样的目录，`retrieve_candidates` 直接返回空 → `diagnose` 走
`needs_human`。于是产品对真实工程的“诊断”实际上不存在，只有夹具工程能诊断；而且诊断
依据是代码文本正则，不是运行证据。这同时违反 P3、P6、P7。

**方向**

把 diagnose 的数据源切到已有的证据候选链（`upi/core/candidates_v2.py` +
`runs/<run>/evidence/`，`webui._build_candidate_ticket_latest` 已经在用），
正则表降级为可选提示，不再作为“候选为空”的闸。

---

## P0-2 修复仍可用“答案参照”生成

**证据**

- `upi/agents/nodes.py:118`：`ref = prof.defect_ref(prof.fix_subject)`，模板从缺陷态参照文件按行切片
- `upi/core/plan_provider.py:31`：`if active_profile().profile_id != "upi-fixture": return None`
- `upi/config/project_profile.py:77,285`：`defect_refs_dir="upi/agents/_refs"`
- 仓库内实际文件：`upi/agents/_refs/F_CPU_01_defect.cs`

**为什么违反**

这是“把答案当模板”：参照文件是缺陷态源码，模板按行号切成 `find/replace`。
`fixture` 门又把它限定在夹具工程。产品默认修复路径在源码配方不可用时仍会落到这里
（`default_plan_provider` → `fixture_cpu_plan`），违反 P5、P6。

**方向**

删除 `_refs` 与 `defect_ref` 产品通路（保留为测试夹具也可以，但不得在产品默认路径）；
源码配方不可用就 `needs_human`，不回落答案。

---

## P0-3 产品默认身份是夹具工程

**证据**

- `upi/config/project_profile.py:39`：`DEFAULT_PROFILE_ID = "upi-fixture"`
- `upi/config/project_profile.py:338-347`：内置档案 `project_path=fixtures/upi-fixture`、
  `fix_subject="F-CPU-01"`、`subject_file=fixtures/.../CombatSkillManager.cs`
- `upi/core/unity_exec.py:33-40`：默认场景 = `scene_of(prof.fix_subject)`，没有 `fix_subject` 就返回 None
- `upi/core/unity_exec.py:105`：无 `fix_subject/scene` → 拒绝执行
- `upi/agents/verify.py:186-188`：重采命令 `--fixtures <fixture>`，只认夹具 id

**为什么违反**

没有激活工程时，产品默认跑夹具；执行/验证的场景选择绑在 `fix_subject` 上。
真实工程没有这个字段，执行器直接拒绝。违反 P6，并让“真实工程可用”变成一句空话。

**方向**

- 取消夹具作为默认档案；没有激活工程就明确“未选择工程”。
- 场景/工作负载从 replay/套件/当前打开场景来，不从 `fix_subject` 来。
- verify 用 replay 标识工作负载，不用 `--fixtures`。

---

## P0-4 标定硬依赖“干净基准”，且阈值随仓库提交

**证据**

- `upi/agents/patrol.py:376-380`：`clean_subject` 为空 → `blindspot`，直接拒标
- `upi/agents/daemon.py:574-581`：守护自动标定走同一个 `calibrate_round`
- `scripts/m1_multiwin.py:582-585`：`do_merge` 缺 CLEAN 数据 → `return 1`，阈值生不出来
- `upi/__main__.py:77-80`：`upi status` 把 `baselines/thresholds_*.json` 的存在当作健康条件
- 仓库已提交：`baselines/thresholds_*.json`（3 份）、`baselines/baseline_*.json`（3 份）
- `upi/tooling/onboarding.py:205-207`：产品向导要求“噪声基准必须同轮在场，缺它按采集失败拒判”

**为什么违反**

标定要的是“本机仪器噪声”，实现却要求“一个干净基准场景”，并把它固化成仓库里的阈值文件。
这正好同时踩中你的两条批评：跨机器不可迁移、真实工程没有干净版。违反 P1、P4、P2。

**方向**

- 标定只量“同一 workload 重复 N 次”的复现噪声，per machine、per 协议指纹；
  没有干净场景时走 L0（绝对下限），不拒标。
- 阈值文件本地化（机器级目录），不进 git、不跨机共享。
- `status` 不再以“有阈值文件”为健康前提。

## P1-5 守护/巡检以“夹具清单”为单位

**证据**

- `upi/agents/daemon.py:230-247`：`fixtures` 默认取 `profile.fixture_universe()`，缺失/不匹配告警
- `upi/agents/patrol.py:433-442`：水通路按 `cfg["fixtures"]` 采一轮束
- `upi/agents/patrol.py:6-7`：文档写明“CLEAN 同轮在场才可比”

**为什么违反**

产品的工作单位是“工程 + 工作负载”，不是“夹具列表”。真实工程没有 `F-CPU-01` 清单，
巡检无从开始。违反 P6。

**方向**

巡检单位改为“工程 + replay/场景 + 指标预算”，夹具列表只属于评测。

---

## P1-6 静态机会扫描仍是产品入口，且规则按病例代码调过

**证据**

- `upi/core/opportunity.py:28-47`：9 条正则（含 `roundText.text = "ROUND "`、
  `new Texture2D(2, 2` 这类按当前病例代码写的特征）
- `upi/core/opportunity_planner.py:119-122`：`_SOURCE_ANCHOR` 把 pattern 映射到写死的方法名
  （`ChromaGame.UpdateHudBody`、`BoardModel.FindMatches`）
- `upi/agents/webui.py:1352`：`/api/tickets/opportunities` 仍可直接建单

**为什么违反**

即使已声明“不计分”，它仍是用户能点的产品入口；规则按病例代码调过，换工程即失效，
属于 P3 的“匹配模式”。方法名硬编码还违反 P6。

**方向**

明确降级为“启发式线索（不建单、不进入修复）”，或在产品里移除；若要保留，
规则必须是通用语义（如 `new Material(`），不得包含病例专属文本。

---

## P1-7 评测闸在读产品档案（且导入期取一次）

**证据**

- `upi/tooling/checklist.py:63,70`：模块导入时 `FIXTURE_SPEC = active_profile().fixture_spec`、
  `CLEAN_ID = active_profile().clean_subject`
- `upi/agents/nodes.py:602`：record 节点直接 `checklist_for_proposal()`（隐式读当前档案）
- `upi/tooling/report_data.py:30`：报告层同样依赖

**为什么违反**

评测语义通过“当前激活档案”进入产品路径；档案一换（或为空），闸的结果跟着变，
且导入期缓存使测试/进程状态互相污染。违反 P2。

**方向**

`checklist` 改为显式传 spec/clean id；record 记录“本次提案用的评测输入”，
不读全局档案。

## P1-8 学习库提交了夹具运行结果

**证据**

- `knowledge/patterns.db`：`outcomes` 2 条，`fixture='F-CPU-01'`、`profile='upi-fixture'`
- `knowledge/fingerprints.db`：6 条内置指纹（机制级，尚可）
- `upi/core/knowledge.py` 用这些 outcomes 算成功率/`n_effective`

**为什么违反**

把夹具上的“成功”作为产品先验发货，等于夹带夹具答案；违反 P2、P8。
指纹是机制级（`metric+shape`），这条是合规的。

**方向**

运行库与种子库分离：种子只放机制级指纹；夹具 outcomes 留在评测侧，不进产品 DB。

---

## P1-9 运维脚本仍把夹具路径写死

**证据**

- `scripts/m1_calibrate.py:68`、`scripts/m1_multiwin.py:582`、`scripts/m1_detect.py:374`
- `scripts/m3_rehearsal.py:38-39`、`scripts/m4_drill.py:37-40,181`
- `scripts/e2e_*.py`、`scripts/run_exp*.py` 等十余处 `fixtures/upi-fixture`

**为什么违反**

这些脚本是当前检测/标定/彩排的实际执行体（`nodes.py:232` 直接子进程调 `m1_detect.py`），
不是纯实验代码。产品的工作负载被写死在夹具上。违反 P6。

**方向**

参数化 `--project/--replay/--fixtures`，默认从激活工程与套件取；夹具路径只留在测试脚本。

---

## P1-10 接入向导仍要求“噪声基准”

**证据**

- `upi/tooling/onboarding.py:123,205-207`：向导询问并展示 `clean_subject`
- 文案：“采束时必须同轮在场，缺它按采集失败拒判（L2 前提，不降级）”

**为什么违反**

把评测概念（CLEAN）作为接入必填项/推荐项，违反 P1、P2；且与设计文档
`knowledge/下限目标与噪声基准设计.md` §1“噪声基准缺失 ⇒ 口径降级，不是整轮拒判”直接矛盾。

**方向**

向导不询问 CLEAN；默认 L0；需要相对判据时用“同 workload 重复采样”的噪声。

---

## P2-11 “降级”与“拒判”的口径冲突

`knowledge/下限目标与噪声基准设计.md`（§1）说降级，代码 `patrol.calibrate_round`、`m1_multiwin.do_merge`
说拒判；`onboarding` 文案又说拒判。三处口径不一致，需要统一为“降级 + 明确标注”。

## P2-12 源码配方按夹具方法名分发

`upi/core/source_plan.py` 与 `upi/core/repair_recipe.py` 按 `UpdateHud`、
`RefreshItemLabels`、`FindMatches` 这类符号分发；换工程/换命名即无方案。
当前是“诚实拒绝”，但能力面窄；属于 P3 的轻度残留（按名字匹配能力）。

## P2-13 指纹库的 builtin 规则与夹具指标绑定

`upi/core/fingerprint.py:264` 的 builtin 指纹以 `metric+shape` 建（机制级，合规），
但内置的 6 条与夹具的指标集一一对应，换工程可能无命中；需要补“未命中即转人工”的默认叙事，
而不是把它当通用能力。

## P2-14 UI 暴露夹具语义

`upi/agents/webui.py:249,717` 展示 `fix_subject`；设置页仍有“修复机制/主体文件”概念。
UI 是唯一人机入口（G23），这里会把夹具模型教给用户。

## P2-15 `_SOURCE_ANCHOR` 写死方法名

`upi/core/opportunity_planner.py:119-122` 把 `ui_text_rebuild_per_frame` 映射到
`ChromaGame.UpdateHudBody`。换工程即失效，且是“按名字给答案”的轻度形态。

## 已经对齐的部分（不是全盘否定）

- `knowledge/frame_budget.json`：绝对帧预算，写明“不是标定产物、不是调参结果”，
  是“没有正确答案”范式下的合法参照。
- `upi/core/floor_check.py`：绝对下限腿，不依赖干净基线。
- `upi/core/findings.py` + `scripts/capability_run.py`：能力结论只来自运行证据，
  不读 oracle、不匹配 pattern。
- `upi/core/source_plan.py`：`find` 必须精确命中一次，否则拒绝，不硬写。
- `upi/core/holdout.py`：泄漏检查只在评测侧。
- `upi/` 没有 import `sim/`（oracle 未进产品）。

## 建议的整改顺序

| 步 | 内容 | 影响面 |
|---|---|---|
| R1 | 诊断切证据候选；删除 `_refs`/`defect_ref` 产品通路与 `upi-fixture` 门 | P0-1、P0-2 |
| R2 | 取消夹具默认档案；场景/工作负载改为 replay/套件；verify 去 `--fixtures` | P0-3、P1-9 |
| R3 | 标定改“同 workload 重复采样”；无干净场景走 L0；阈值本地化、移出 git | P0-4、P2-11 |
| R4 | 静态扫描降级/移除；清单闸显式传参；学习库种子与运行分离 | P1-6、P1-7、P1-8 |
| R5 | 向导/UI 去夹具语义；文档口径统一；配方按语义（非方法名）扩展 | P1-10、P2-12~15 |

## 审查边界

- 本报告基于静态阅读与 grep，未逐条运行所有分支；行号以当前工作区为准。
- `sim/`、`fixtures/` 是评测资产，未按产品标准审查。
- 修复工作量：R1/R2 大（改诊断与执行数据源），R3 中，R4/R5 小。
