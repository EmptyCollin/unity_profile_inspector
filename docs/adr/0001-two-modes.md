# ADR-0001：两种运行形态（常驻 / 回归）

- 状态：已接受（I0，2026-11-11）
- 决策者：用户 + 开发
- 关联：`docs/回放准入标准.md`、`DESIGN.md`、`AGENTS.md`

## 背景

工具要同时服务两个场景：

1. **日常开发**：开发者在编辑器里跑游戏，性能越界或抽检异常时，希望工具
   尽快给一个可回滚的改法。这个场景没有稳定的回放，无法做复现验证。
2. **批量回归**：有稳定回放指令和测试目标，需要证明“这个问题真的修好了”，
   并批量交付。

把两者压成一个“全自动 Agent”会导致：日常模式被迫承担它做不到的验证责任；
回归模式被日常噪声拖慢。

## 决策

工具分两个运行形态，共享同一套 probe / event / cluster / fingerprint /
playbook / patch / rollback 核心：

| 维度 | 常驻形态 | 回归形态 |
|---|---|---|
| 数据源 | 常驻探针 + 1Hz 哨兵/抽检 | 确定性 replay + 测试目标 |
| 问题定义 | 预算线 / 相对基线 / 抽检异常 | replay 指令 + 测试目标 |
| 复现 | 不要求 3 次基线 | 3 次（或 N 次）基线 + 聚类 + 复现率 |
| 修复 | best-effort，编译/冒烟/可回滚 | 修 + 同 replay 重跑 + 重新聚类 |
| 结论 | `unverified`，不进成功率分母 | `verified`，进成功率 |
| 节奏 | 常驻 / 实时 | 批量 / 夜间 / CI / 里程碑 |

**硬规则**：

- 常驻形态的修复不得声称 `resolved` 或 `verified`；只能记 `unverified`。
- 回归形态的 `verified` 必须来自“同 replay、同 cluster 消失、无新 cluster、
  守护不劣化”。
- 两形态的统计分账：`mode ∈ resident|regression`、
  `verification_status ∈ unverified|observed|verified`。

## 后果

- 常驻模式可以轻、快、低门槛；回归模式可以重、严、可审计。
- 需要新增 `BatchTicket`、`PatchAttempt`、`Observation` 等契约（ADR-0003）。
- 回放准入标准只约束回归形态，不再要求日常模式也有确定性回放。
- 常驻修复的补丁必须可追溯到 commit/patch ID，供回归模式验证或回滚。

## 不做什么

- 不把常驻模式做成“盲改”：安全验证（编译/启动/异常/回滚）仍然必须。
- 不把回归模式做成“全游戏优化”：只对 replay + 测试目标负责。
