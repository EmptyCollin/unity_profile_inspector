# ADR-0002：UI 技术栈——本地 Web，标准库优先

- 状态：已接受（I0，2026-11-11）
- 关联：ADR-0001、`upi/agents/webui.py`

## 背景

用户要求：**UI 是本工具人机交互的唯一通道**。现有 ANSI TUI（`upi/agents/ui.py`）
能表达的状态有限；工单、证据链、回归基线矩阵一旦复杂，就退化成“让人读 JSON”。

候选：

1. **FastAPI + HTMX + SSE**：开发体验好，但要新增依赖（本机未安装 FastAPI）。
2. **Python 标准库 `ThreadingHTTPServer` + 服务端 HTML + SSE**：零依赖、离线可用、
   与仓库“可审计、可离线”的取向一致；代价是路由/模板要自己写。
3. **桌面壳（Tauri/Electron）**：引入 Node/前端构建链，太重，不符合轻量目标。

## 决策

I0 采用 **方案 2：标准库本地 Web + SSE**。

- 只绑 `127.0.0.1`，随机 token，`HttpOnly` cookie；
- 服务端渲染 HTML；前端只用原生 JS + SSE，不引入 Node/CDN；
- 图表后续用手写 SVG/Canvas（与现有报告层一致）；
- `upi ui` 启动服务并打开浏览器；`--check` 做 HTTP 自检；`--port 0` 分配端口。

## 后果

- 零新增依赖，任何有 Python 的机器都能开控制台；离线可用。
- 路由、CSRF、模板转义要自己守；I5 前补齐 API 测试与浏览器冒烟。
- 如果后续页面复杂度超过标准库承载能力，再评估 FastAPI；本 ADR 不阻挡升级，
  但升级必须保留“本地、离线、无 Node 构建”的约束。

## 不做什么

- 不做 LAN/远程访问；不做多用户权限体系。
- 不把阈值/权限编辑放进 UI（仍走 blocked 流程）。
- 不在 I0 假装工单/回归页面已可用；它们只显示占位，I3/I4/I5 接入。
