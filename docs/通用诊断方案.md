# I8：通用诊断与源码级修复（设计稿，待审）

> 目的：把当前“**能测指标、但根因候选仍靠正则/模板**”的链路，升级成
> “**运行时证据 → 候选根因 → 可校准置信度 → 从当前源码生成修复 → 同 replay 验证**”。
>
> 专项 case（devsim 24 case）可以作为开发/回归/负对照，但**不能同时充当最终泛化证据**；
> 最终结论必须另有未见过的 holdout。

---

## 0. 先定义问题

当前不是“纯匹配”，但也没有达到通用诊断：

| 层 | 现状 | 问题 |
|---|---|---|
| 运行时检测 | probe 采帧级指标（CPU/GPU/GC/drawCalls/animator/loading） | 只有指标，没有函数级/对象级归因 |
| 候选根因 | `candidate_retrieval.py` 用正则扫 `.cs`，生成机制模板 | 候选被正则上限锁死；不是从证据反推 |
| 归因 | LLM 六因子 + `c_attr` 公式 | 输入证据太薄；只有点估计，没有区间 |
| 修复 | `_plan_for(anchor)` 固定 playbook；机会路径固定模板 | 只能修已知模式；换工程/换写法就失效 |
| 泛化 | devsim/testlab | 没有“未知问题”验证；case 参与了主路径 |

**I8 的核心不是加 pattern，而是把“模式”降级为 priors（先验），把证据和源码分析升级为主路径。**

---

## 1. 目标与非目标

### 目标

1. 能在**未预先编码**的性能问题上，产出 top-k 候选根因；
2. 根因能落到**函数/调用栈/渲染对象/分配点**，而不是只落到“某文件某行”；
3. 置信度是**可校准的区间**，不是拍脑袋分数；
4. 修复计划从**当前源码**生成，不依赖预置 anchor diff；
5. 专项 case 可以参与开发调试，但不能同时用于“最终泛化声明”；必须另建未见过的 holdout；
6. 至少在一个 holdout 集和一个第二工程上验证泛化。

### 非目标

- 不替代 Unity Profiler / RenderDoc；
- 不做全引擎 instrumentation；
- 不承诺所有性能问题都能自动修；
- 不把 Deep Profile 的耗时数据当作正式性能数据；
- 不在第一版覆盖全部 GPU/Shader/物理/网络问题。

## 3. 证据层 Evidence v2

### 3.1 新增证据类型

```text
CallStackSample
  frame_idx, thread, sample_weight
  frames[]: {symbol, source_file, line, native?}
  metric_context

FunctionStat
  marker/symbol, calls_per_frame, total_ms, self_ms
  source_span, first_seen_frame

RenderObjectStat
  renderer_path, material_ids[], shader
  draw_calls, batches, triangles, frame_idx

AllocationSite
  bytes, count, stack[], source_span, frame_idx

CodeSymbol
  file, span, kind, signature, containing_type
```

### 3.2 采集方式

按“可用性探测 → 降级”实现，不假设 Unity 版本一定有某个 API：

| 证据 | 首选 | 降级 |
|---|---|---|
| 函数耗时/调用次数 | `ProfilerRecorder` marker | 只有帧指标，标 `unavailable` |
| 托管调用栈 | Unity Profiler binary log / deep profile | 仅采样帧，标 `sampling_only` |
| 对象级 draw call | FrameDebugger / Profiler 渲染统计 | 只有总 drawCalls |
| 分配点 | GC 分配调用栈（若可用） | 只有 `gc_alloc_per_frame` |
| 代码符号 | tree-sitter / Roslyn sidecar | 文件+行+文本窗口 |

**硬规则：**

- Deep Profile 只用于归因，不用于性能判定；
- 采集开销超过预算 → 标 `instrument_distorted`，该轮不得用于结论；
- 拿不到调用栈必须写 `unavailable`，不能假装“没有调用栈=没有热点”；
- 所有原始文件落 `runs/<id>/evidence/`，不得只把摘要喂给 LLM。

## 4. 证据图与候选生成

### 4.1 图结构

节点：

```text
Metric → FrameWindow → Cluster
FrameWindow → CallStackSample → Function → CodeSymbol
FrameWindow → RenderObjectStat → Material/Shader
FrameWindow → AllocationSite → CodeSymbol
```

边表示“同帧/同窗口/同调用/同对象/同源”。

### 4.2 候选生成规则

候选不再来自：

```text
正则命中 new List< → 根因模板
```

而是来自：

1. **热点函数**：调用栈 self/total 高的函数；
2. **异常对象**：draw call/材质/批次数显著高于同类的 renderer；
3. **异常分配点**：分配字节/次数高的调用栈；
4. **代码锚点**：函数符号 → 源码 span；
5. **指纹先验**：历史 pattern 只提高 `prior_hit` 权重，不作为候选门槛；
6. **未知候选**：允许生成“当前指纹库没有”的新候选，标 `novel`。

### 4.3 指纹库的新定位

- 指纹 = **prior**，不是 route/gate；
- 命中只影响 `prior_hit` 因子；
- 未命中不拒绝，只降低先验；
- 机制级签名仍禁止文件名/类名/函数名进入签名（DESIGN §8.3）。

## 5. 置信度与区间

### 5.1 两个不同的不确定性

1. **指标不确定性**：同一协议多次采样，median 的 bootstrap 区间；
2. **归因不确定性**：六因子判定 + 权重不确定性，Monte Carlo 得到 `c_attr` 分布。

### 5.2 输出

```text
Hypothesis:
  confidence_point
  confidence_interval_80
  interval_basis: bootstrap | monte_carlo | prior_only
  veto_reasons[]
  evidence_refs[]
```

路由建议：

- `point < 0.6` 或 `interval_low < 0.5` → `needs_human`；
- 只有 `interval_low >= 0.6` 才允许进入自动修复候选；
- 区间不能由 LLM 填，只能由采样/权重/公式产生。

### 5.3 校准

- 用 holdout 的“预测根因 vs 实际根因”做 reliability diagram；
- 报 ECE、Brier、top-k；
- 校准不达标 → 置信度只作排序，不作自动修复依据。

## 6. 源码级修复

### 6.1 修复计划来源

```text
候选根因 + 证据图 + 源码符号
→ 机制级 repair recipe
→ 当前源码 span
→ 生成 diff
→ 编译/断言/权限
```

`repair recipe` 是**参数化操作**，不是固定文件行：

- 缓存字段提取；
- 对象池复用；
- 共享材质/MPB；
- 异步加载；
- 脏标记/节流；
- 合批策略。

### 6.2 不依赖预置 anchor

- 不允许 `_plan_for(anchor)` 直接返回固定 diff；
- 每个 diff 必须能追溯到候选根因和证据；
- 生成失败 → `needs_human`，不硬编；
- 修复后必须同 replay 验证，不能只编译。

### 6.3 与现有门禁的关系

保留：

- G4 快照；
- G8 编译门禁；
- G9 回滚只靠 git；
- G19 逐帧源；
- G20 盲区清单；
- 权限矩阵、逐项批准、失败回滚。

## 7. 验证与泛化

### 7.1 专项 case 的新定位：可以调参，但不能自证泛化

需要把“隔离 oracle”和“未知问题”分开：

- **隔离 oracle** 只去掉答案文件，去不掉作者知识、case 设计、`legacy_*` 开关、case_id、注释和场景选择；
- devsim 的代码里本身有 `legacy_*`、`case_id`、`DevSimScenarios` 映射，这些就是**标签泄漏**；
- 因此即使 oracle 在工程外，devsim 对实现者仍然是**已知问题**。

正确做法是分成三套：

| 集合 | 用途 | 是否可调参 | 是否可对外报泛化 |
|---|---|---|---|
| **D 开发集**（devsim 24） | 调试、回归、负对照 | 可以 | 不可以 |
| **H 留出集** | 冻结后只跑一次 | 不可以 | 可以 |
| **X 外部工程** | 真实未知分布 | 不可以 | 最强证据 |

硬规则：

1. **不能靠“把标签从输入里过滤掉”**：LLM 看到注释、命名、结构就能语义推断，过滤不是安全边界；
2. 诊断引擎只接收 `EvidenceBundle`；但更重要的是**工程本身不含测试标签**；
3. replay harness 在工程外，可以用 seed/输入/存档布置世界，但不能把 case 语义写进被测工程；
4. H 集在冻结后不得再用于改阈值、改权重、改 prompt、改 pattern；
5. 如果 H 失败，只能记录失败并新建下一版 H，不能回头调参再把同一 H 报成通过；
6. D 集上提升不等于泛化，报告必须同时给 D/H 差值。

**所以：把 oracle 挪到工程外，只去掉“答案文件”这一类泄漏；它不会自动把 devsim 变成未知问题。**

真正的“未知”不是靠过滤器造出来的，而是靠**工程真实性**：

- 工程里没有 `legacy_*`、`case_id`、`DevSimScenarios` 这种测试语义；
- 没有“故意保留”“缺陷”“case”这类注释；
- 测试开关/棋盘注入/replay 驱动在工程外，或至少在诊断扫描范围外；
- 被测工程是“一个真实项目快照”，不是“一个带答案开关的演示工程”；
- 机制被改名、搬位置、换写法后仍能识别；
- 评测集在调参冻结前没有被人看过；
- 最好还有非本团队写的工程。

### 7.2 项目真实性：把 devsim 当生产项目

这一条比“诊断输入过滤”更重要：

1. **删除测试专用语义**：`legacy_*`、`case_id`、`DevSimScenarios`、`DebugSetBoard` 等不进入被测工程主代码；
2. **测试驱动外置**：case 选择、盘面注入、seed、期望结果放 `sim/driver` 或外部 harness，不放进工程；
3. **只通过正常入口操作**：replay 用游戏输入/存档/场景加载，不用“按 case 名改分支”；
4. **一个 case = 一个真实代码快照/构建**，不是“一个 runtime flag”；
5. **注释也要真实**：不写“这里故意埋的”“这是性能缺陷”；
6. **诊断扫描范围固定**：只扫生产代码，不扫测试驱动；但 LLM 仍可能从生产代码语义推断，所以根本还是工程要干净。

如果做不到“无测试语义”，就只能把它标成 **D 开发集**，不能拿来证明泛化。

### 7.3 指标

| 指标 | 说明 |
|---|---|
| localization@1/3 | 根因代码位置 top-k |
| attribution@1/3 | 根因机制 top-k |
| interval coverage | 真实根因落在区间内的比例 |
| ECE | 置信度校准误差 |
| repair_success | 编译+守护+同 replay 通过 |
| novel_recall | 指纹库外问题的检出率 |
| holdout_delta | tuning vs holdout 差距 |

### 7.4 泛化门槛（建议）

- 至少 1 个 **未参与开发** 的 H 集（冻结后只跑一次）；
- 至少 1 个第二工程；
- 诊断输入不含 case_id/flags/oracle；
- novel_recall ≥ 0.5；
- interval coverage ≥ 0.7（80% 区间）；
- 自动修复只在 `interval_low ≥ 0.6` 且编译/守护通过时允许；
- 不达标就不扩 auto 权限。

## 8. 分阶段实施

### I8a：证据 v2（先不改变诊断结论）

- 调用栈/函数统计/对象级 draw call/分配点采集；
- 可用性探测 + 降级标记；
- 原始证据落盘；
- 验收：能对一个 devsim 场景输出“帧 → 栈 → 函数 → 源码 span”。

### I8b：证据图与候选生成

- 建图；
- 从热点函数/对象/分配点生成候选；
- 指纹只做 prior；
- 验收：在一个**未编码**的问题上产出 top-3 候选。

### I8c：置信区间

- bootstrap + Monte Carlo；
- 校准集/holdout；
- 验收：区间覆盖率和 ECE 达标。

### I8d：源码级修复

- 符号/AST span；
- 参数化 repair recipe；
- 编译/回滚/验证；
- 验收：至少 2 类新问题不靠固定 anchor 修复。

### I8e：泛化验收

- holdout + testlab + 外部工程；
- 专项 case 只做回归；
- 验收：novel_recall、holdout_delta、repair_success 达标。

## 9. 风险与边界

| 风险 | 处理 |
|---|---|
| Profiler API 版本差异 | 运行时探测，缺失标 unavailable |
| Deep Profile 改性能 | 只用于归因，不用于判定 |
| 调用栈开销大 | 采样/按需开启，默认关闭 |
| 栈符号解析失败 | 保留原始地址/帧，不猜函数 |
| LLM 幻觉 | 只判定因子；数值/证据由工具给 |
| 新候选过多 | top-k + 证据门槛 + human gate |
| 外部工程未验证 | 明确标 `external_unverified`，不冒充泛化 |

## 11. 失败、重试与人工降级

先纠正一句话：

> **“失败就是失败”只适用于评测口径；任务级失败必须重试和降级。**
>
> 产品不能因为一次修复失败就停住；但也不能把在 H 集上失败后“回头调参再报通过”叫泛化。

### 11.1 两种失败必须分开

| 失败类型 | 含义 | 正确处理 |
|---|---|---|
| **任务失败** | 某个 Issue 的一次诊断/修复没通过 | 回滚 → 换假设/补证据 → 重试 → 预算耗尽转人工 |
| **评测失败** | 某个版本在冻结的 H 集上没通过 | 记录该版本失败；在 D 集改能力；下一版换新 H 重测 |

任务失败不能直接终止产品；评测失败也不能靠重跑同一个 H 洗白。

### 11.2 任务级状态机

```text
candidate
  → diagnosing
  → planned
  → snapshot
  → applied
  → verifying
      ├─ pass      → keep / next issue
      ├─ retryable → rollback → 新假设/补证据 → 重试
      └─ terminal  → rollback → needs_human
```

每次重试必须带：

```text
retry_reason
strategy_delta     # 这次和上次有什么不同
new_evidence[]     # 新增了什么证据
previous_diff_hash # 禁止原样重试
```

没有 `strategy_delta` 的重试直接拒绝。

### 11.3 失败分类与路由

| 失败 | 处理 | 是否消耗 Issue 预算 |
|---|---|---|
| 编译失败 | 回滚；修 plan；重试 | 是 |
| 目标指标未改善 | 回滚；换假设；重试 | 是 |
| 守护指标劣化 | 回滚；同机制停止；进 Review/人工 | 是 |
| 感知门禁失败 | 回滚；直接人工 | 否，立即升级 |
| 证据不足 | 补采样/Deep Profile/静态分析；仍不足转人工 | 是 |
| 工具/编辑器不可用 | 基础设施重试；不污染 Issue 预算 | 否 |
| 权限/不安全改动 | 拒绝；转人工 | 否 |
| 同一失败重复 2 次 | 停止自动重试；转人工 | 是 |

### 11.4 预算与无进展检测

- `max_attempts_per_issue` 默认 3；
- `max_review_rounds` 默认 3；
- wallclock / token 全局预算；
- 同一 Issue 连续两次 `same_failure + same_diff_hash` → `needs_human`；
- 连续两次没有新增证据 → `needs_human`，禁止“再试一次”空转；
- 每次失败都写 `AttemptRecord`，包含证据、diff、verdict、回滚结果。

### 11.5 转人工不是“丢掉”

转人工必须交一个可审的包：

```text
issue + evidence
已尝试的假设[] + 每次 diff
每次 verdict / 回滚结果
当前盲区[]
建议的下一步（补采样/改代码/人工判断）
```

UI 上必须能：

- 看到每次尝试；
- 批准/拒绝下一步；
- 选择“继续自动”“换方向”“终止”；
- 终止后保留完整证据链。

人修完后：

- 作为 **D 集新样本**回归；
- 不能直接塞进 H 集；
- 如果形成新 pattern，走权限升维流程，不自动放宽。

### 11.6 评测失败后的能力循环

H 集失败时：

1. 记录 `H-failure`，该版本结果保持失败；
2. 在 D 集定位能力缺口：证据、候选、归因、修复、预算；
3. 修能力，不在 H 上调参；
4. 下一版用 **新的 H 版本** 重测；
5. 如果只是基础设施/协议问题（编辑器挂起、协议指纹不一致），可在**代码/模型未变**的前提下重跑同一 H，并记录 `infra_retry`。

### 11.7 “高泛用”怎么落地

泛用不是“永不失败”，而是：

- 失败能自动换策略；
- 缺证据能自动升级采集；
- 超出能力能正确转人工；
- 人工处理后能沉淀成新能力；
- 新能力在**新 H/外部工程**上复测，而不是在旧 H 上自证。

---

## 12. 需要你审的决策点

1. 第一版范围：先做 **CPU/GC + drawCalls** 竖切，还是一次覆盖 GPU/Shader？
   - 建议先 CPU/GC + drawCalls；GPU 逐笔归因仍转人工。
2. 调用栈采集：接受 **Deep Profile 仅归因、不用于性能判定** 吗？
3. 置信区间：接受“校准区间”，不冒充严格频率置信区间吗？
4. 自动修复权限：是否只允许 `interval_low ≥ 0.6` 且编译/守护通过？
5. 验收：是否接受“devsim 必须去掉 case_id/legacy/测试注入语义，否则只能当 D 集；最终结论另建未见过的 H 集”？
6. 外部工程：第一版是否只承诺 testlab 代理，不承诺任意第三方？
7. 是否接受“干净测试只能保证测得公平，不能保证 Agent 一定泛化；失败就是失败，不回头加提示”？
8. 任务失败是否接受“默认 3 次重试，连续 2 次同失败/无新证据转人工”，而不是一次失败就停？
9. 评测失败是否接受“该版本保持失败，能力在 D 集修，下一版换新 H 复测”，而不是重跑旧 H 洗白？

## 13. 一句话

**I8 不是“再加检测模式”，而是把工具从“已知模式修复器”改成“证据驱动的诊断器”。**

专项 case 继续保留：可以用于开发/回归，但不能用自己的答案证明自己泛化；最终结论必须来自未参与调参的 H 集或外部工程。
