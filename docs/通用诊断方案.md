# I8：通用诊断与源码级修复（设计稿，待审）

> 目的：把当前“**能测指标、但根因候选仍靠正则/模板**”的链路，升级成
> “**运行时证据 → 候选根因 → 可校准置信度 → 从当前源码生成修复 → 同 replay 验证**”。
>
> 专项 case（devsim 24 case）只作为**验收/回归/负对照**，不再作为产品诊断的主路径。

---

## 0. 先定义问题

当前不是“纯匹配”，但也没有达到通用诊断：

| 层 | 现状 | 问题 |
|---|---|---|
| 运行时检测 | probe 采帧级指标（CPU/GPU/GC/drawCalls/animator/loading） | 只有指标，没有函数级/对象级归因 |
| 候选根因 | `candidate_retrieval.py` 用正则扫 `.cs`，生成机制模板 | 候选被正则上限锁死；不是从证据反推 |
| 归因 | LLM 六因子 + `c_attr` 公式 | 输入证据太薄；只有点估计，没有区间 |
| 修复 | `_plan_for(anchor)` 固定 playbook；机会路径固定模板 | 只能修已知模式；换工程/换写法就失效 |
| 泛化 | devsim/testlab | 没有“未知问题”验证；case 参与了主路径 |

**I8 的核心不是加 pattern，而是把“模式”降级为 priors（先验），把证据和源码分析升级为主路径。**

---

## 1. 目标与非目标

### 目标

1. 能在**未预先编码**的性能问题上，产出 top-k 候选根因；
2. 根因能落到**函数/调用栈/渲染对象/分配点**，而不是只落到“某文件某行”；
3. 置信度是**可校准的区间**，不是拍脑袋分数；
4. 修复计划从**当前源码**生成，不依赖预置 anchor diff；
5. 专项 case 只用于验证，不参与候选生成和调参；
6. 至少在一个 holdout 集和一个第二工程上验证泛化。

### 非目标

- 不替代 Unity Profiler / RenderDoc；
- 不做全引擎 instrumentation；
- 不承诺所有性能问题都能自动修；
- 不把 Deep Profile 的耗时数据当作正式性能数据；
- 不在第一版覆盖全部 GPU/Shader/物理/网络问题。

## 3. 证据层 Evidence v2

### 3.1 新增证据类型

```text
CallStackSample
  frame_idx, thread, sample_weight
  frames[]: {symbol, source_file, line, native?}
  metric_context

FunctionStat
  marker/symbol, calls_per_frame, total_ms, self_ms
  source_span, first_seen_frame

RenderObjectStat
  renderer_path, material_ids[], shader
  draw_calls, batches, triangles, frame_idx

AllocationSite
  bytes, count, stack[], source_span, frame_idx

CodeSymbol
  file, span, kind, signature, containing_type
```

### 3.2 采集方式

按“可用性探测 → 降级”实现，不假设 Unity 版本一定有某个 API：

| 证据 | 首选 | 降级 |
|---|---|---|
| 函数耗时/调用次数 | `ProfilerRecorder` marker | 只有帧指标，标 `unavailable` |
| 托管调用栈 | Unity Profiler binary log / deep profile | 仅采样帧，标 `sampling_only` |
| 对象级 draw call | FrameDebugger / Profiler 渲染统计 | 只有总 drawCalls |
| 分配点 | GC 分配调用栈（若可用） | 只有 `gc_alloc_per_frame` |
| 代码符号 | tree-sitter / Roslyn sidecar | 文件+行+文本窗口 |

**硬规则：**

- Deep Profile 只用于归因，不用于性能判定；
- 采集开销超过预算 → 标 `instrument_distorted`，该轮不得用于结论；
- 拿不到调用栈必须写 `unavailable`，不能假装“没有调用栈=没有热点”；
- 所有原始文件落 `runs/<id>/evidence/`，不得只把摘要喂给 LLM。

## 4. 证据图与候选生成

### 4.1 图结构

节点：

```text
Metric → FrameWindow → Cluster
FrameWindow → CallStackSample → Function → CodeSymbol
FrameWindow → RenderObjectStat → Material/Shader
FrameWindow → AllocationSite → CodeSymbol
```

边表示“同帧/同窗口/同调用/同对象/同源”。

### 4.2 候选生成规则

候选不再来自：

```text
正则命中 new List< → 根因模板
```

而是来自：

1. **热点函数**：调用栈 self/total 高的函数；
2. **异常对象**：draw call/材质/批次数显著高于同类的 renderer；
3. **异常分配点**：分配字节/次数高的调用栈；
4. **代码锚点**：函数符号 → 源码 span；
5. **指纹先验**：历史 pattern 只提高 `prior_hit` 权重，不作为候选门槛；
6. **未知候选**：允许生成“当前指纹库没有”的新候选，标 `novel`。

### 4.3 指纹库的新定位

- 指纹 = **prior**，不是 route/gate；
- 命中只影响 `prior_hit` 因子；
- 未命中不拒绝，只降低先验；
- 机制级签名仍禁止文件名/类名/函数名进入签名（DESIGN §8.3）。

## 5. 置信度与区间

### 5.1 两个不同的不确定性

1. **指标不确定性**：同一协议多次采样，median 的 bootstrap 区间；
2. **归因不确定性**：六因子判定 + 权重不确定性，Monte Carlo 得到 `c_attr` 分布。

### 5.2 输出

```text
Hypothesis:
  confidence_point
  confidence_interval_80
  interval_basis: bootstrap | monte_carlo | prior_only
  veto_reasons[]
  evidence_refs[]
```

路由建议：

- `point < 0.6` 或 `interval_low < 0.5` → `needs_human`；
- 只有 `interval_low >= 0.6` 才允许进入自动修复候选；
- 区间不能由 LLM 填，只能由采样/权重/公式产生。

### 5.3 校准

- 用 holdout 的“预测根因 vs 实际根因”做 reliability diagram；
- 报 ECE、Brier、top-k；
- 校准不达标 → 置信度只作排序，不作自动修复依据。

## 6. 源码级修复

### 6.1 修复计划来源

```text
候选根因 + 证据图 + 源码符号
→ 机制级 repair recipe
→ 当前源码 span
→ 生成 diff
→ 编译/断言/权限
```

`repair recipe` 是**参数化操作**，不是固定文件行：

- 缓存字段提取；
- 对象池复用；
- 共享材质/MPB；
- 异步加载；
- 脏标记/节流；
- 合批策略。

### 6.2 不依赖预置 anchor

- 不允许 `_plan_for(anchor)` 直接返回固定 diff；
- 每个 diff 必须能追溯到候选根因和证据；
- 生成失败 → `needs_human`，不硬编；
- 修复后必须同 replay 验证，不能只编译。

### 6.3 与现有门禁的关系

保留：

- G4 快照；
- G8 编译门禁；
- G9 回滚只靠 git；
- G19 逐帧源；
- G20 盲区清单；
- 权限矩阵、逐项批准、失败回滚。

## 7. 验证与泛化

### 7.1 专项 case 的新定位

devsim 24 case：

- 只做 **验收/回归/负对照**；
- 不参与候选生成；
- 不参与阈值/权重调参；
- 不把 case id 写进 planner。

### 7.2 指标

| 指标 | 说明 |
|---|---|
| localization@1/3 | 根因代码位置 top-k |
| attribution@1/3 | 根因机制 top-k |
| interval coverage | 真实根因落在区间内的比例 |
| ECE | 置信度校准误差 |
| repair_success | 编译+守护+同 replay 通过 |
| novel_recall | 指纹库外问题的检出率 |
| holdout_delta | tuning vs holdout 差距 |

### 7.3 泛化门槛（建议）

- 至少 1 个 **未参与开发** 的 holdout 集；
- 至少 1 个第二工程；
- novel_recall ≥ 0.5；
- interval coverage ≥ 0.7（80% 区间）；
- 自动修复只在 `interval_low ≥ 0.6` 且编译/守护通过时允许；
- 不达标就不扩 auto 权限。

## 8. 分阶段实施

### I8a：证据 v2（先不改变诊断结论）

- 调用栈/函数统计/对象级 draw call/分配点采集；
- 可用性探测 + 降级标记；
- 原始证据落盘；
- 验收：能对一个 devsim 场景输出“帧 → 栈 → 函数 → 源码 span”。

### I8b：证据图与候选生成

- 建图；
- 从热点函数/对象/分配点生成候选；
- 指纹只做 prior；
- 验收：在一个**未编码**的问题上产出 top-3 候选。

### I8c：置信区间

- bootstrap + Monte Carlo；
- 校准集/holdout；
- 验收：区间覆盖率和 ECE 达标。

### I8d：源码级修复

- 符号/AST span；
- 参数化 repair recipe；
- 编译/回滚/验证；
- 验收：至少 2 类新问题不靠固定 anchor 修复。

### I8e：泛化验收

- holdout + testlab + 外部工程；
- 专项 case 只做回归；
- 验收：novel_recall、holdout_delta、repair_success 达标。

## 9. 风险与边界

| 风险 | 处理 |
|---|---|
| Profiler API 版本差异 | 运行时探测，缺失标 unavailable |
| Deep Profile 改性能 | 只用于归因，不用于判定 |
| 调用栈开销大 | 采样/按需开启，默认关闭 |
| 栈符号解析失败 | 保留原始地址/帧，不猜函数 |
| LLM 幻觉 | 只判定因子；数值/证据由工具给 |
| 新候选过多 | top-k + 证据门槛 + human gate |
| 外部工程未验证 | 明确标 `external_unverified`，不冒充泛化 |

```text

upi/core/repair_recipe.py    # 参数化修复
```

改造：

```text
candidate_retrieval.py  -> 只保留为 priors/兼容，不再主路径
nodes.diagnose          -> 接证据图与区间
nodes._plan_for          -> 接 source-aware recipe
probe/upi_probe_v4.cs    -> 可选 deep capture 模式
```

**不做双读/双跑兼容**：新链路直接替换旧候选生成；旧 case 只做回归，不保留 fallback。

## 11. 需要你审的决策点

1. 第一版范围：先做 **CPU/GC + drawCalls** 竖切，还是一次覆盖 GPU/Shader？
   - 建议先 CPU/GC + drawCalls；GPU 逐笔归因仍转人工。
2. 调用栈采集：接受 **Deep Profile 仅归因、不用于性能判定** 吗？
3. 置信区间：接受“校准区间”，不冒充严格频率置信区间吗？
4. 自动修复权限：是否只允许 `interval_low ≥ 0.6` 且编译/守护通过？
5. 验收：是否接受“专项 case 不参与调参，另建 holdout”？
6. 外部工程：第一版是否只承诺 testlab 代理，不承诺任意第三方？

---

## 12. 一句话

**I8 不是“再加检测模式”，而是把工具从“已知模式修复器”改成“证据驱动的诊断器”。**

专项 case 继续保留，但只做验尸/回归，不再当诊断本身。
